# 2.9.3 版本体验反馈

来源：2.9.3 实机体验。四个问题：

1. **还没走到核心跟前，怪已经在打核心，计时也在跑。** → H1–H3
2. **地狱第 4 层压力太大**（每波 15 只、同屏 10 只，是 4 层就该有的强度吗）。→ H4
3. **限时房没有任何倒计时，打着打着突然"时间到"，一直以为是普通房。** → B1
4. **房间目标一完成就自动进下一间，传送门形同虚设。** → H5

本文全部条目**只写方案，不改代码**；如果实施，落在 **2.9.4**（下文代码注释里的 `2.9.4` 都是这个意思）。

> 另：核对 §6 的时序时顺手查出一个**现在就存在**的真 bug —— 清房结算可以被重复触发，
> 见 §6.8（已用探针复现，附数据）。

> 原「空中闪避体力没有正常减少」一条已删除：经实测与确认，那是**滞空之羽**的效果（空中闪避不耗体力），
> 不是 bug。完美闪避把体力回满也是既有设计，一并保留。

## 0. 一句话方案

- **H1–H3**：给 `holdZone` 加一个 `started` 门闩 —— 没进圈之前，时间不走、波次不刷、怪不打核心；
  玩家第一次踏进护罩的那一帧，三件事一起打开。`started` 随 `holdZone` 重建而归零，
  所以"每次进守点房都重置"是天然的，不需要额外的清理代码。
- **H4**：每波数量从"难度定死"改成"**层数线性 + 难度乘数**"，
  普通难度基准 **第 3 层 5 只 → 第 15 层 15 只**，同屏上限由每波数量派生。
- **B1**：限时房的倒计时**有，但和普通房的"剩余敌人"共用同一行小字**，场景里又是空的，
  所以读起来就是普通房。**选 A + C**：A 给房间内独占倒计时 + 进度条（无美术），
  C 加一个场景实体（蜡烛/沙漏，需美术）。
- **H5**：删掉「房间目标完成 → 立刻开地图进下一间」，下一间只能靠**走进传送门**触发（1 行）。
- **H5 二期（§6.7）**：连结算也挪到门上 —— 清房只开门，进门才结算金币 + 弹三选一。

## 1. 现象一：进门就开打

现状 `startHold()`（战斗2D.js:14813）一执行——也就是**进房间那一刻**——就：

| 立刻发生 | 位置 | 后果 |
|---|---|---|
| `H.t` 每帧 +dt | updateHold 15046 | 16 秒倒计时从进门开始跑 |
| `waveAt = [0, 4000, 8000]`，`H.t >= 0` 立即成立 | updateHold 15052 | 第 1 波 0.8s 后进场 |
| `enemyAim()` 无条件返回 `{core:true}` | 16068 | 近战/冲锋/掷矛/子弹四条路径全部打核心 |

算一下时间账（普通 10 层）：核心 120 血，`dmgNormal 6 × mul(1+10×0.03)=1.3` → 单次 8，
`hitCd 300ms` → 一只近战贴住核心约 26 DPS，4.6 秒碎。
圈心落在 `levelWidth × 0.55`（pickCoreSpot 14889），从入口走过去要 2~4 秒——
**玩家还在半路上，核心已经掉了一半甚至见底**，护罩根本没机会起作用。

而守点房是 `node.noEnemies = true`（8611），进门时房间里一只怪都没有，
那 2~4 秒的空房间里唯一在发生的事就是"核心在被空气打"。

## 2. 现象二：地狱 4 层压力过大

现在每波数量只跟难度走，跟层数完全无关（MECH_DIFF 755–771）：

| 难度 | 每波 | 同屏上限 | 三波合计 |
|---|---|---|---|
| 简单 | 5 | 4 | 15 |
| 普通 | 7 | 6 | 21 |
| 困难 | 10 | 8 | 30 |
| 地狱 | **15** | **10** | **45** |

第 4 层的地狱房和 40 层的地狱房，刷出来的怪一样多。
4 层玩家的输出/血量还没起来，却要吃 45 只、同屏 10 只 —— 这就是"压力太大"的来源。
反过来，15 层之后地狱仍然只有 45 只，又偏轻了（那时候玩家已经很能打）。

## 3. H1–H3：袭击由进圈触发

### H1 计时从进圈开始
`H.t` 只在玩家**进入护罩范围**之后才推进。进圈之前进度弧为 0，HUD 显示"待启动"。

### H2 怪从进圈开始才打核心
`started === false` 时，`enemyAim()` 一律返回玩家 —— 也就是**完全退回 2.9.1 的索敌**，
原逻辑（`_aggroHeroUntil` 转火、打谁、走位）一行不改，只在最前面加一个条件。

### H3 重置语义
"第一次"以**一次 `startHold()` 的生命周期**为单位：
每次进守点房都会 `destroyHoldZone()` + 重建 `holdZone`（14814 / 14853），`started` 跟着新建为 `false`。
一旦 `started = true` 就不再回退——**玩家中途跑出圈，袭击继续、怪继续打核心**（护罩减伤失效），
这跟现在的"离开圈计时照走"一致，不要改成"出圈暂停"。

### 3.1 状态字段（startHold，14853）

```js
started: false,        // 玩家是否已踏入护罩（H1/H2 的门闩）
startAt: 0,            // 踏入那一帧的 time.now（调试/验证台用）
```

`lastInputAt` 现在在构造时就写成 `this.time.now`（14867），要挪到"开始那一刻"重置，
否则玩家在门口站了 3 秒再进圈，一进去就立刻被判挂机扣血。

### 3.2 进圈检测 + 开门（新增 `tryStartHold`）

```js
/** H1：玩家第一次踏进护罩 → 袭击开始（时间/波次/核心仇恨三件事一起开） */
tryStartHold(H, time) {
  var h = this.hero;
  if (!h || this.heroDead) return false;
  // 判定口径与护罩一致，但用 r0：收缩还没发生，用 r 会和后面 0.8r 的判定打架
  if (Math.abs(h.x - H.x) > H.r0) return false;
  if (Math.abs((h.y - 20) - H.y) > H.r0 * 0.9) return false;

  H.started = true;
  H.startAt = time;
  H.t = 0; H.prog = 0; H.got = 0;
  H.waveIdx = 0;                       // 从第 0 波重来（waveAt[0] = 0，本帧就会排队）
  H.lastInputAt = time; H.idleAt = 0;  // 挂机计时从这里起算
  if (this.roomObjective) this.roomObjective.got = 0;
  this.showCenter('袭击开始 · 守住核心 ' + Math.round(H.dur / 1000) + ' 秒', '#ffd76a');
  sfx('holdStart');
  return true;
}
```

`H.waveIdx = 0` 之后，`while (H.waveIdx < waveAt.length && H.t >= waveAt[H.waveIdx])`
在 `t = 0` 时会命中 `waveAt[0] = 0`，第一波自然排队 + 0.8s 预警——**不需要单独调 `queueWave`**。

### 3.3 updateHold 早退（15040）

```js
// H1：没进圈 → 时间不走、波次不刷、不判挂机；只把护罩画出来（休眠态）
if (!H.started) {
  this.tryStartHold(H, time);
  this.drawHoldZone(time);
  return;
}
```

早退一次挡掉四件事：时间轴（15046）、波次 while（15052）、护罩收缩（15059）、挂机判定（15066）。
出口判定（15079）也不会误触发。

### 3.4 enemyAim 一行（16068）

```js
enemyAim(e, time) {
  var H = this.holdZone, h = this.hero;
  if (!H || !H.coreAlive || H.ended || this.heroDead || !h) { ... }   // 原样
  if (!H.started) return { x: h.x, y: h.y, core: false };            // ← 新增（H2）
  if (time < (e._aggroHeroUntil || 0)) return { x: h.x, y: h.y, core: false };  // 原样
  return { x: H.coreX, y: H.coreY, core: true };                     // 原样
}
```

**这一行就够**：`e._aimCore` 只在 16132 由 `enemyAim` 的结果赋值，
四条伤害路径（近战 `enemyStrike` 16449 / 冲锋 16187 / 掷矛 16506 / 子弹 16602）全都读 `_aimCore`，
所以它们会一起退回"打玩家"，不需要逐条改。

### 3.5 damageCore 守卫（14949）

```js
if (!H || !H.coreAlive || H.ended || H.frozen) return 0;
if (!H.started) return 0;        // ← 新增：开始前的任何来源都不能伤核心
```

双保险。挡的是绕过 `_aimCore` 的路径（现在没有，但落石/陷阱类以后可能加），
也让"开始前核心掉血"变成一个**不可能状态**，测试可以直接断言。

### 3.6 表现层

| 位置 | 现在 | 改成 |
|---|---|---|
| startHold 中央提示 14874 | 「守点房 · 守住核心 16 秒…」 | 「守点房 · **走进青色护罩，袭击才会开始**」 |
| HUD 目标行 13233 | `袭击 16s · 核心 100%` | 未开始时 `待启动 · 核心 100%` |
| 核心头顶文字 14846/15070 | `袭击 16s · 核心 100%` | 未开始时 `走近核心 · 未启动` |
| drawHoldZone 15013 | 进度弧恒画、护罩 alpha 固定 | `started === false` 时不画进度弧，护罩 alpha 压到 0.28 + 慢呼吸（周期 1.6s） |

休眠态的作用是"可读"：玩家一进门就能看出**这圈是可以走进去的开关**，而不是装饰。
不加新美术资源，全部用现有的 `shieldCalm` + 现有 Graphics。

### 3.7 回退开关（已定：加）

项目惯例是"结构性改动都要有开关"（TOGGLES，701）：

```js
var TOGGLES = { oneWay: true, tricolor: true, channel: true, stomp: true, holdGate: true };
```

`updateHold` 的早退条件写成 `if (!H.started && TOGGLES.holdGate)`，
`enemyAim` / `damageCore` 的守卫也带上 `TOGGLES.holdGate`。
关掉 `holdGate` 就回到 2.9.3 的"进门即开打"，一行 `API.setToggles({holdGate:false})` 可回退。

## 4. H4：刷怪数随层数线性

### 4.1 曲线

```js
// CORE 里新增（放在 CORE.reward 附近）
waveCurve: { lo: 5, hi: 15, floorLo: 3, floorHi: 15 },
```

- 机制从第 3 层起（MECHANIC.minFloor），所以 `floorLo = 3`，此处基准 = **5 只**；
- **第 15 层封顶 15 只**，之后不再涨（普通难度）；
- 15 层以后压力仍然在涨，只是改由核心血量（+2/层）和单次伤害（`×(1+层×0.03)`）承担，
  数量封顶是刻意的 —— 同屏怪太多会变成"糊成一团"，读不出走位。
- 曲线很陡（12 层涨 10 只，平均每层 +0.83）：4 层 6 只、10 层 11 只。
  这是"低层松、高层硬"的直接代价 —— 中段（8~12 层）会比现在明显更硬，见 §8 的旋钮。

### 4.2 公式

```js
var t = clamp((floor - 3) / (15 - 3), 0, 1);
var base = 5 + 10 * t;                       // 普通基准 5 → 15
var perWave = clamp(Math.round(base * tune.waveMul), 3, 24);
var cap     = clamp(Math.round(perWave * 0.8), 3, 14);   // 同屏上限由每波派生
```

难度只改**乘数**，不再写死数量（MECH_DIFF 755–771）：

| 难度 | `waveMul`（新） | 原 `perWave` / `cap`（删） |
|---|---|---|
| 简单 | 0.7 | 5 / 4 |
| 普通 | 1.0 | 7 / 6 |
| 困难 | 1.3 | 10 / 8 |
| 地狱 | 1.6 | 15 / 10 |

`MECH_DIFF.hold` 里的 `perWave` / `cap` 两个字段换成 `waveMul`，
`mechanicParams('hold')`（14769）里现算 `perWave` / `cap` 后返回，下游（`rollWaveKinds`、`updateWaveQueue`）不用改。

### 4.3 改完的实际数值

每波数量 / 同屏上限（`floorHi = 15`，15 层起封顶）：

| 层 | 简单 | 普通 | 困难 | 地狱 |
|---|---|---|---|---|
| 3 | 4 / 3 | **5** / 4 | 7 / 6 | 8 / 6 |
| **4** | 4 / 3 | **6** / 5 | 8 / 6 | **9** / **7** |
| 6 | 5 / 4 | 8 / 6 | 10 / 8 | 12 / 10 |
| 10 | 8 / 6 | 11 / 9 | 14 / 11 | 17 / 14 |
| 13 | 9 / 7 | 13 / 10 | 17 / 14 | 21 / 14 |
| **15+** | 11 / 9 | **15** / 12 | 20 / 14 | 24 / 14 |

三波合计（每波 × 3）：

| 层 | 简单 | 普通 | 困难 | 地狱 |
|---|---|---|---|---|
| 3 | 12 | 15 | 21 | 24 |
| **4** | 12 | 18 | 24 | **27**（原 45） |
| 10 | 24 | 33 | 42 | 51（原 45） |
| 15+ | 33 | 45 | 60 | 72 |

**地狱 4 层从 45 只降到 27 只，同屏从 10 降到 7** —— 这是这次改动最主要的目标。
代价是高层变重：普通 10 层从 21 只涨到 33 只、15 层 45 只；地狱 10 层 51 只、15 层 72 只。

对比一下现网（每波 5 / 7 / 10 / 15，与层数无关）：

| 层 | 普通 现网 → 新 | 地狱 现网 → 新 |
|---|---|---|
| 4 | 21 → **18** | 45 → **27** |
| 10 | 21 → **33** | 45 → **51** |
| 15+ | 21 → **45** | 45 → **72** |

也就是说**第 6~7 层是分水岭**：之前比现在轻，之后比现在重（普通 6 层 24 只已超现网 21 只）。
这是"第 15 层吃满"的必然结果 —— 如果实测觉得中段太硬，最省事的旋钮是 §8 的 B（把 `floorHi` 挪到 20）。

### 4.4 顺带：远程怪比例（已定：**不做**，保持每波至少 2 只远程）

`rollWaveKinds`（15092）现在固定"每波至少 2 只远程"，每波 5 只时远程占 40%，
低层会显得特别凶。**这条已决定不做**，下面只是留档（万一以后低层仍觉得凶，改法现成）：

```js
var wantRanged = clamp(Math.round(n * 0.25), 1, H.forceRanged ? 4 : 3);
```

| 每波 n | 原 | 新 |
|---|---|---|
| 4 | 2 | 1 |
| 8 | 2 | 2 |
| 13 | 2 | 3 |
| 15 | 2 | 3（上限） |

高台强制远程时上限放宽到 4，保证"圈落在高台"那条规则仍然有牙。

### 4.5 需要留意：排队积压（曲线变陡后会提前出现）

`updateWaveQueue` 是 350ms 一只（CORE.queueCd），所以一间房的"排队产能" = `dur / 350ms`：

| 难度 | dur | 产能 | 三波总量封顶 | 从第几层开始溢出 |
|---|---|---|---|---|
| 简单 | 14s | 40 只 | 33 | 不溢出 |
| 普通 | 16s | 45 只 | 45 | 刚好（45 / 45.7） |
| 困难 | 18s | 51 只 | 60 | **14 层起**（54 只） |
| 地狱 | 20s | 57 只 | 72 | **12 层起**（60 只） |

- 影响：不是 bug（"压力叠加"是设计意图），但高难度高层的最后一波会**没刷完就到时间**，
  玩家实际面对的怪比表上的数字少，"清空提前结束"这个出口也基本不会触发。
- 如果实测觉得糊：把 `queueCd` 改成随数量缩短，`clamp(350 - perWave * 8, 200, 350)`；
  24 只 → 200ms，产能翻到 100。**已定：不改**（保持 350ms，积压先当设计意图看）。
- 曲线越陡，积压越早：15 层吃满的这版比"20 层才吃满"的方案提前 3~4 层开始溢。

## 5. B1：限时房没有可见的倒计时

### 5.1 现象

在一间看起来完全普通的房间里打怪，突然弹出「时间到 · 敌人强化」，才知道这是限时房。
全程没有任何"这房有时限"的持续信号。

### 5.2 实测：倒计时在，但读起来就是普通房

探针 `测试/限时房HUD探针.html`（第 10 层建一间 timed 房，直接读 HUD 元素的文本）：

```
HUD 右上      「限时 30s · 敌人 11」      颜色 #e86878（danger，恒定）
顶部房间名     「房间:普通房间 · 限时 · 已探索 1/6」
中央提示       「限时房 · 30 秒内清空」   2.2s 后 alpha = 0.00
房间内实体     无（timedRoom 上没有 text / gfx 任何对象）
```

| 信号 | 位置 | 问题 |
|---|---|---|
| 中央提示 | `startTimed` 15280 | `showCenter` 1.1s 后开始淡出、0.5s 淡完（13197），**1.6 秒后彻底消失** |
| HUD 右上「限时 30s · 敌人 11」 | `refreshHud` 13236 | 与普通房的「剩余敌人 11」**同一元素、同一 13px、同一颜色**（3670） |
| 房间名「普通房间 · 限时」 | 13272 | **房间类型本来就叫"普通房间"**，"限时"两个字缩在中间，玩家第一眼读到的是前四个字 |
| 房间内 | — | **空的，没有任何实体** |

根因不是"没做倒计时"，而是三条叠加：
1. **位置与样式复用**了普通房的目标行，只换了文字 —— 玩家扫 HUD 读到的是"敌人 11"；
2. **房间名直接写着"普通房间"**，等于官方告诉玩家这是普通房；
3. 那个倒计时**一直是 danger 红**（`#e86878` 是元素的基础色），所以"快没时间了"没有任何颜色变化可读。

三个机制里，塌陷有"地面在塌 + 魂晶"，守点有"核心 + 护罩"，
**只有限时房在场景里一件东西都没有** —— 所以它是唯一会"以为是普通房"的那个。

### 5.3 改法（已定：A + C，B 不做）

**A. 给限时房一个属于自己的倒计时（无美术，约 30 行）**

照抄 `holdZone` 的那套（15273 起）做文本 + 进度条，但**锚点要换**：守点的文字钉在核心上（world-space），
限时房没有这样的锚点，必须贴在屏幕上，否则玩家跑到房间两端就看不见。

```js
// startTimed 里，与 timedRoom 一起建
// ⚠️ 贴屏幕（scrollFactor 0），不要放在房间中央：限时房玩家会跑遍整间，
//    房间内的固定文本走到两端就出屏了 —— 那正是"看不到倒计时"的老问题
var T = this.timedRoom;
var cx = this.scale.width / 2, cy = this.hudSafeTop() + 44;
T.text = this.add.text(cx, cy, '', { fontFamily: FONT, fontSize: '15px',
  color: '#ffd76a', fontStyle: 'bold' }).setOrigin(0.5).setScrollFactor(0).setDepth(900);
T.gfx  = this.add.graphics().setScrollFactor(0).setDepth(900);
// updateTimed 里逐帧：条宽 = 剩余比例；≤5s 转红 + 每秒一次脉动
```

（守点的核心文本是 world-space，因为核心钉在一个位置上；限时房没有这样的锚点，所以必须贴屏幕。）

- HUD 那行退回只显示「敌人 N」，避免两处重复（否则还是老问题：信息挤在一行里）；
- **三档配色**（现在是恒定 danger 红，等于没有信号）：
  `>10s` 暖金 `#ffd76a` / `5~10s` 橙 `#ffa25a` / `≤5s` 红 `#ff5d7a` + **每秒一次**缩放脉动 + `sfx('tick')`
  （没有 tick 就复用 `sfx('error')` 降音量）；
- 超时那一帧：文本换成「时间到 · 敌人强化」并保持 2.5s 不淡出；

## 6. H5：删掉「完成即进下一间」，让传送门重新有意义

### 6.1 现象

房间目标一完成，奖励面板就弹出来；选完奖励**直接开地图**进下一间 —— 全程不需要走到右边的传送门。
塌陷房最明显：捡完最后几颗魂晶，三选一弹出来，点完就换房，门连看都没看一眼。

### 6.2 根因

奖励与"进下一间"是**同一个调用链上的两件事**：

| 环节 | 位置 | 作用 |
|---|---|---|
| 目标完成 → 开门 | `openPortal`（战斗2D.js 15466） | 门变亮 + 发 `rt:room-cleared` |
| 宿主收到清房 | `onRoomCleared`（经典2D.js 1514） | 结算金币 + 弹奖励三选一 |
| **选完奖励 → 进下一间** | `onChoiceResult` → **`advanceToNextRoom()`**（经典2D.js 1619 → 1706） | `e.press('map')` 直接开地图 |
| 走进传送门 | `nextFloor()`（战斗2D.js 15560） | 非 Boss 房 → `openMap()` |

问题就在第三行：`advanceToNextRoom()` 里的 `e.press('map')` 让"选完奖励"和"走进传送门"等价，
后者被彻底绕过。同一个函数还被遗物面板、商店、事件房、裂隙、结局面板等十来处调用，所以**所有**面板结束后都在自动换房。

### 6.3 改法

**删掉非 Boss 分支里的 `e.press('map')`**，只留一条注释说明这里曾经有什么：

```js
// 经典2D.js 1726 附近
// 2.9.4：这里原本是 `try { e.press('map'); } catch (err) { ... }` ——
// 「房间目标完成 → 立刻开地图进下一间」，玩家根本不用走到传送门，
// 门因此没有存在感（塌陷房最明显：捡完魂晶马上选奖励就走人）。
// 该机制已删除：下一间只能靠走进传送门触发（引擎 nextFloor → openMap）。
```

Boss 房分支**不动**：那里的 `advanceToNextRoom()` 负责弹「深渊裂隙」和「结局面板」，
是层末流程，不是"跳过门"。而且引擎注释里写明 Boss 房不能由宿主开地图（开了就走不进传送门，会卡死）。

### 6.4 改完后的完整流程

```
目标完成 → 门变亮（中央提示「XX已清空 · 走向右方传送门」）
        → 金币结算 + 奖励三选一（还在房间里，门就在右边）
        → 玩家自己走到传送门 → 地图 → 选下一间
```

> 这是**只做 H5**时的流程。再做 §6.7（二期）之后，金币结算与三选一会整体挪到"走进门"那一刻。

### 6.5 影响面

| 流程 | 改动前 | 改动后 |
|---|---|---|
| 战斗房（含塌陷 / 守点 / 限时） | 选完奖励自动开地图 | 必须走到门 |
| 精英 / 镜像 / 宝箱房 | 同上 | 必须走到门 |
| Boss 房 | 打完自动进裂隙 / 结局 | **不变**（层末流程不是"跳过门"） |
| 商店 / 休整 / 事件 / 宝箱 | 面板关掉自动开地图 | 必须走到门 |
| 遗物三选一 | 选完自动开地图 | 必须走到门 |

风险：玩家可能在空房间里找不到出口。缓解手段已经有 —— 开门时中央提示"走向右方传送门"，
且 `updateGuide` 会在门不在屏内时给方向箭头。

### 6.6 验证

1. 普通战斗房：清完 → 三选一 → **不出现地图**，门亮着；走到门口 → 地图打开；
2. 塌陷房：捡满魂晶 → 门开 + 三选一 → 点完仍在房间里；
3. 商店房：买完关门 → 仍在房间里，走到门才换房；
4. Boss 房：打完 → 三选一 → 裂隙面板 → 结局面板（与改动前一致）；
5. 站在门口时不要"关地图立刻又弹开"——`_portalGraceUntil` 已有 500ms 宽限，改动后路径更单一，不需要额外处理。

### 6.7 后续（已定要做）：奖励也挪到门后

H5 只解决了"不自动进下一间"，奖励仍在清房瞬间发。既然要让门有分量，就把**结算也挪到门上**：
清房只开门，**走进门**才结算金币 + 弹三选一。

#### 现状时序

```
目标完成 → openPortal() ─┬─ 门变亮 + 中央提示
                        ├─ _floorRoomsCleared++
                        ├─ checkpointState → rt:room-cleared → 宿主：金币 + 三选一
                        └─ 存档
        → 玩家走到门 → nextFloor() → openMap()
```

结算发生在开门那一刻，门只是"下一步按钮"。

#### 目标时序（两段式过门）

```
目标完成 → openPortal()：只门变亮 + 中央提示（不结算）
        → 玩家走到门 → nextFloor()：
              ① settleRoomClear()（清房数 +1 + 快照 + rt:room-cleared → 宿主弹三选一）
              ② _awaitClearAck = true; return        ← 停在这里
              ③ 之后每帧再进来：if (_awaitClearAck) return   ← 必须挡住
        → 宿主处理完（三选一 / 遗物 / 失守放行）→ API.ackRoomCleared()
        → nextFloor() 再进一次：portalOpen = false → openMap() / 换层
```

#### 改动清单 · 引擎（战斗2D.js）

| # | 位置 | 改法 |
|---|---|---|
| 1 | `openPortal` 15476–15497 | 把 `if (first) { 命运轮盘 / _floorRoomsCleared++ / pulseAt / checkpointState / emitRt / notifyCheckpoint }` 整块抽成 `settleRoomClear()`；`openPortal` 只留"门变亮 + 中央提示" |
| 2 | `nextFloor` 15560 | 开头插入两段：①`if (!this._roomSettled) { this._roomSettled = true; this.settleRoomClear(); this._awaitClearAck = true; return; }` ②`if (this._awaitClearAck) return;`。⚠️ ②不能省 —— `updateHero` 每帧都在门口调 `nextFloor()`，少了它下一帧就直接开地图，奖励还没弹完。`previewMode` 分支必须排在这之前（预览页没有宿主，等不到 ack 会卡死） |
| 3 | 新增 | `ackRoomCleared()`：`this._awaitClearAck = false; this.nextFloor();` |
| 4 | API | 导出 `ackRoomCleared`（宿主调用） |
| 5 | 房间重置 | 每间房 `_roomSettled = false; _awaitClearAck = false;`（和 `portalOpen = false` 同一处，8631 / 14870） |
| 6 | `debug()` | 暴露 `settled` / `awaitAck`，便于断言 |

#### 改动清单 · 宿主（经典2D.js）

| # | 位置 | 改法 |
|---|---|---|
| 7 | `onRoomCleared` 1514 | 逻辑不变（金币 + 三选一），只是触发时机变成"过门" |
| 8 | `onChoiceResult` 1619 | 非 Boss：结尾从 `advanceToNextRoom()` 改成 `e.ackRoomCleared()`；Boss 保持 `advanceToNextRoom()`（裂隙 / 结局），结局面板关掉后再 ack |
| 9 | 失守 / 非战斗房 | 没有面板要弹，`onRoomCleared` 里直接 ack |

#### 边界

- **重复过门**：`_roomSettled` 保证每间房只结算一次；`_awaitClearAck` 挡住"贴着门连续触发"。
- **死亡**：门开但没进门就死 → 本局结束，奖励没领。这是**新行为**（原来开门就领），
  所以开门提示要改成「XX已清空 · 门后有奖励」。
- **存档**：`notifyCheckpoint('room-cleared')` 移到过门时 → 读档回到"门开、未结算"，再过门结算，不会重复也不会丢。
- **预览页**：`previewMode` 分支保持在 settle 之前，进门直接 `finishPreviewRun()`。
- **Boss 房**：进门 → settle → 三选一 → 裂隙 → 结局 → ack → 换层，顺序不能乱。
- **宿主漏了 ack 会卡在门口**（引擎一直 `_awaitClearAck`）。建议加个兜底：`_awaitClearAck` 超过 3 秒
  自动 `ackRoomCleared()` 并打一条 warn —— 时序类改动最怕"某个分支忘了回话"，宁可放行也别卡死。

#### 回退开关

`TOGGLES.settleAtDoor = true`（新增）。置 false 时 `openPortal` 走回原路（开门即结算并置 `_roomSettled = true`），
`nextFloor` 的第一段直接跳过 —— 一行切回 2.9.3 的行为。

#### 测试影响

| 断言 | 现状 | 改完 |
|---|---|---|
| P4 `_floorRoomsCleared === clearedH + 1`（守点完成即 +1） | 开门时 +1 | 要先 `nextFloor()` 才 +1 |
| P4 `clearedHoldEvt === 1`（`rt:room-cleared`） | 开门时发 | 过门时才发 |
| P0-P3 里涉及 `portalOpen` / 清房数的断言 | — | 需一并核对 |
| 新增 ① | — | 开门后 `settled === false`、`awaitAck === false` |
| 新增 ② | — | 第一次 `nextFloor()` 后 `settled === true` 且 `mapOpen === false` |
| 新增 ③ | — | `ackRoomCleared()` 后 `mapOpen === true` |
| 新增 ④ | — | 重复 `nextFloor()` 不会重复发 `rt:room-cleared` |

#### 成本

引擎约 40 行、宿主约 25 行、测试改 3~4 处 + 新增 4 条。
风险中等（时序类），必须手动验：普通房 / 塌陷 / 守点 / 商店 / 精英 / Boss 各走一遍。

### 6.8 顺带查出的真 bug：清房结算会被重复触发

查 §6.7 的时序时顺手验了一下，发现**现在的代码就有**：清房 → 过门 → 在门上把地图关掉，
`rt:room-cleared` 会再发一次，金币和奖励三选一**再来一遍**，而且可以反复刷。

探针 `测试/清房重复结算探针.html`（清空一间普通房，手动走一遍过门 → 关地图）：

```
① 清空后：  portalOpen=true   cleared=1  evt=1
② 过门后：  portalOpen=false  mapOpen=true  cleared=1  evt=1
③ 关地图后：portalOpen=true   cleared=2  evt=2   ← 重复结算
```

**根因**：`openPortal()` 的去重条件只有 `var first = !this.portalOpen`（15469）。
`nextFloor()` 把 `portalOpen` 置 false，随后 `closeMap()` 里的 `checkFloorClear(true)`（15642）
发现门关着且房间仍是"已清空"，就再调一次 `openPortal()` —— `first` 又变成 true，
于是 `_floorRoomsCleared++`、快照、`rt:room-cleared` 全部重来一遍。

玩家能关地图：地图面板上有关闭按钮（15649），ESC 也关（10299）。所以这不是理论问题。

**改法要分两种情形写，否则会和 §6.7 打架**（两边都置 `_roomSettled` 的话，二期就永远等不到 settle）：

**情形一 · 只做 H5（批次 1）** —— 结算还在 `openPortal` 里，加个"已结算"守卫：

```js
// openPortal，15469
var first = !this.portalOpen && !this._roomSettled;
...
if (first) {
  this._roomSettled = true;      // ← 这间房已经结算过，重开门不再发
  ...原 _floorRoomsCleared / 快照 / emitRt...
}
```

**情形二 · 做完 §6.7 二期之后** —— `openPortal` 里那段已经整体搬进 `settleRoomClear()`，
它只被 `nextFloor` 调一次，`_roomSettled` 也只在 `settleRoomClear()` 里置位；
`openPortal` **不要**再碰 `_roomSettled`，重复结算自然消失（`closeMap` 再开门时门只是"亮着"，不结算）。

一句话：`_roomSettled` 的**唯一写入点**永远是"真正发 `rt:room-cleared` 的那一处"，别在两处都写。

**成本**：2 行 + 1 条断言（`nextFloor()` → `closeMap()` 之后 `evt` 仍为 1、`_floorRoomsCleared` 不变）。

## 8. 预期影响

**H1–H3 会让守点变简单**：玩家白赚 2~4 秒走位时间，等于核心少挨一半的开场伤害。
按普通 10 层估，走到位时核心从原来的 50~70% 变成 90% 以上。

高层更紧（普通 15 层 45 只，原来只有 21 只）。地狱 4 层从 45 降到 27，这是你反馈的那个点。

    `ackRoomCleared()` 之后 `mapOpen === true`；重复 `nextFloor()` 不重复发 `rt:room-cleared`。
12. **重复结算（§6.8）**：`nextFloor()` → `closeMap()` 之后 `rt:room-cleared` 计数仍为 1、`_floorRoomsCleared` 不变
    （探针 `测试/清房重复结算探针.html` 可直接改成断言版）。

### 9.3 手工验收

1. 进守点房 → 房间空着、门锁着、护罩暗着、HUD 写"待启动"；
2. 站着不动 10 秒 → 核心 100%、没有怪、没有倒计时；
3. 走进圈 → 立刻"袭击开始" + 第一波预警（圈边闪 + 两侧裂纹）；
4. 进圈后再跑出圈 → 计时照走、怪继续打核心、护罩减伤失效（跟现在一致）；
5. 打完进下一个守点房 → 又是"待启动"；
6. 地狱 4 层守点 → 每波 9 只、同屏最多 7 只（不是原来的 15 / 10）；
7. 进限时房 → **屏幕上方**能看到倒计时数字与进度条（跑到房间两端也不出屏），剩 5 秒变红并有滴答声；
8. 限时房挂机到超时 → 文本变「时间到 · 敌人强化」；
9. 清空任意房间 → 选完奖励**地图不弹**，门亮着；走到门口才开地图（见 §6.6）；
10. 走到门口 → 地图弹出 → **直接关掉地图** → 奖励与金币**不会**再来一次（见 §6.8）。
