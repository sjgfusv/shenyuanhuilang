## 1. 必修（含一条测试修复）

### 1.1 塌陷房 / 守点房通关不给奖励（P0，影响实际收益）

**现象**

| 房型 | portalOpen | `rt:room-cleared` | `notifyCheckpoint('room-cleared')` | `_floorRoomsCleared` |
|---|---|---|---|---|
| 普通房 | ✅ | 1 次 | 1 次 | 1 |
| **塌陷房** | ✅ | **0 次** | **0 次** | **0** |
| **守点房** | ✅ | **0 次** | **0 次** | **0** |
| 限时房 | ✅ | 1 次 | 1 次 | 1 |

**原因**

`unlockCollapse()`（12524）和 `unlockHold()`（13003）都是直接 `this.portalOpen = true`，绕过了 `openPortal()`。
而 `checkFloorClear()` 第一句就是 `if (this.portalOpen && this.portal) return;` —— 于是 `openPortal()` 里的 `if (first)` 整块永远不执行：

- 遗物「命运轮盘」不触发
- `_floorRoomsCleared++` 不执行 → `pulseInterval()` 不加速
- `emitRt('rt:room-cleared')` 不发 → **宿主 `onRoomCleared()` 收不到**
- `notifyCheckpoint('room-cleared')` 不发 → **不自动存档**

宿主侧 `经典2D.js:1461` 的 `openRewardPanel()` 只挂在 `onRoomCleared` 上，而 `onRoomCleared`（1442）里依次做三件事：

1. `settleRoomGold(roomType)` —— **金币 + 经验**
2. `if (roomType === 'elite') s._pendingRelic = '精英遗物'` —— 精英/层主遗物
3. `if (combat) openRewardPanel()` —— **奖励三选一**

所以实际损失是：**打完一间塌陷房或守点房，没有金币、没有经验、没有三选一、也不存档。** 限时房因为是走 `checkFloorClear → openPortal`，反而一切正常 —— 这也说明不是设计上不要奖励，而是这两条路径漏接了。

**建议改法**

在 `unlockCollapse` / `unlockHold` 的**末尾**（播完本机制自己的 `showCenter` 之后），把 `this.portalOpen = true` 换成：

```
this.portalOpen = false;
this.openPortal(true);   // quiet=true：不要用「房间已清空」覆盖本机制自己的提示
```

顺序很重要：`openPortal(true)` 会设 `portalOpen = true` 并跑完 `if (first)` 整块，但 quiet 模式下不弹通用提示，所以不会盖掉「封印解除 · 出口开启」。

更稳的做法是给 `openPortal` 加一个独立的 `_roomSettled` 标记，把「门开了」和「这间房结算过了」拆成两个状态 —— 现在用 `portalOpen` 兼任两个语义，正是这次漏接的根因。

⚠️ `endCollapse()`（12693）走的是 `unlockCollapse(true)`，同一条路径，一并修。

### 1.2 回归页的 `terrain()` 脚手架会误报（改测试，不是改游戏）

> **更正**：这一条最初被记成「断桥坠落会把玩家甩回缺口左侧」，是**误判**。用完整 `buildLevel` 流程重测 30 次，30/30 正常。真正的问题在测试脚手架。

**现象**：`测试/P0-P3结构回归.html` 的 `terrain()` 是这么写的：

```
s.clearLevel(); s.floor = floor; s.levelWidth = 2560; s.groundY = H - 96;
return s.applySkeleton(sk, params(floor));     // ← 少了 applyCameraBounds()
```

`applyCameraBounds()` 只在 `buildLevel()` 里被调用，它负责 `physics.world.setBounds(0, -600, levelWidth, ...)`。
绕过 `buildLevel` 直接铺地形 → **`levelWidth` 改了、物理世界边界没改**，还是上一间房的宽度。

实测（起始房 levelWidth=1490）：

| 步骤 | levelWidth | worldBounds.right |
|---|---|---|
| 起始 | 1490 | 1490 |
| 绕过 buildLevel 铺 2560 的断桥 | 2560 | **1490（没变）** |
| 走 buildLevel 铺断桥 | 2200 | 2200 |

后果：任何「传送到 x > 旧边界」的用例都会被世界边界截住 —— 英雄被卡在 `1490 - 13(半宽) = 1477`，看起来就像「被甩回缺口左侧」。所以：

- 游戏里不会发生（`buildLevel` 一定调 `applyCameraBounds`，`onResize` / `setSkeletonMode` 也都走 `buildLevel`）；
- 但**回归页会稳定误报**，而且不同窗口尺寸下旧边界不同，报出来的数字还不一样（我手动复现时是 1477，第一次跑那一页时是 1515，都是「旧边界 − 半宽」）。

**建议**：`terrain()` 里补一行 `s.applyCameraBounds();`（或干脆改成 `s._forceSkeleton = sk; s.buildLevel(node); s._forceSkeleton = null;`，走完整流程）。
同时把「掉落传送」用例改成先建一间**宽度正确**的房再测，否则这条用例永远是假阴性/假阳性。

## 2. 与文档 / 验收口径不符

### 2.1 战斗中的 2D 图鉴没有「地形与机制」

- DOM 图鉴（`主程序.js getEncyclopediaData`）已加，共 11 类。
- **画布内图鉴 `codexTabs()`（5783）仍是 10 个 tab**，没有这一栏。
- 玩家在一局里按「菜单 → 图鉴」查不到塌陷 / 三色魂晶 / 踩头。
- 依据：§1.1 不变量 5「新房间/新机制进图鉴」。

**建议**：给 `codexTabs()` 加 `{ id:'terrain', label:'地形' }`，条目直接调 `API.getCodexData().entries`（同源，不另抄）。

### 2.2 图鉴守点文案与代码不符

`getCodexData()` 里写「圈内每秒都在挨打，**清完才开门**」。
实际 `unlockHold()` 到点直接开门，不检查敌人数量 —— 玩家可以带着一屋子怪走人。

**建议**：改文案为「到点即开门，不必清怪」；或者反过来，在 `unlockHold` 里加 `if (alive>0) return;` 让行为对齐文案。二选一，别留两份说法。

### 2.3 层数变体没做

- 初步设想 §11.2 第 8 条是**拍板要做**的；施工清单 §7.2 验收也写了「层数变体按初步设想 §9.1 的表生效（段数/间隔/魂晶需求/平台数）」。
- 代码里 `mechanicParams()`（12896）只按难度缩放，注释明确写「层数只用于奖励与敌人强度，不再改机制参数」。

**建议**：要么补（`segments/interval/need` 按层数分三档即可，表已经在文档里），要么回写两份文档，注明「改为难度单轴，理由：实测 8/4.0/3 在普通难度成立」。别让文档继续挂着一条没做的验收。

### 2.4 塌陷只能挂平厅（只影响约 9% 的战斗房）

**先把范围说清楚**：塌陷是**机制**，只挂在约 15% 的战斗房上；骨架是每个战斗房必选的维度。两者相乘，和塌陷有关的只有三格：

| 形态 | 占全部战斗房 | 现状 |
|---|---|---|
| 平厅 + 塌陷 | ≈ 6% | 正常 |
| 双层 + 塌陷 | ≈ 5.25% | **被强制降级成平厅** |
| 断桥 + 塌陷 | ≈ 3.75% | **被强制降级成平厅** |
| 其余 9 格（含守点 / 限时 / 无机制） | ≈ 85% | 不受影响，也不该被这次改动碰到 |

`buildLevel`（7596）：`if (mech === 'collapse') this._forceSkeleton = 'flat';`
施工清单 §7.2 验收要求「平厅 / 双层 / 断桥三种骨架都能挂塌陷，且都成立」。

所以这条的实质不是"给塌陷加三种骨架"，而是**把那 9% 被改写的骨架还回去** —— 投放率不动，变的只是这 15% 内部的地形。

**根因不是"少写了分支"**：塌陷的压力来自"脚下的地形会消失"，所以任何不会消失的地形都会变成安全区 —— 浮台是（已删），双层上层也是（更大更好站）。断桥则是另一个方向：缺口把地面切碎，塌陷没地方塌。

**方案已单独出**：`其他/塌陷机制-多骨架方案.md`。核心两条：

- **双层 × 塌陷**：上层不逐段塌，而是**下层塌到一半时整块崩塌**（约 15s 预警、17s 崩落），崩塌后房间退化为平厅塌陷。上半场垂直、下半场平铺，一个房间里两种空间感。
- **断桥 × 塌陷**：**缺口就是"初始已塌"的块**，剩余地面按缺口切分成 6 块继续塌；挂塌陷时缺口数固定 1、块数 6、间隔放宽到 4.5s（**只对这一格生效**，断桥 × 守点 / 限时仍按 1~2 个缺口）。

落地顺序建议：先把"均分 N 段"抽象成"地形块列表"（平厅塌陷行为不变）→ 接断桥（验证抽象）→ 接双层（动上层对象）→ 最后删掉 `_forceSkeleton='flat'`。验收里必须有一条「非塌陷房一行不动」。

> 顺带更正我第一轮的判断：`startCollapse()` 确实能在断桥上跑起来（它只按启用的地砖分组），但分组边界仍按全宽均分、而且会把上层平台一起销毁 —— **能跑 ≠ 成立**，不能靠"去掉那行 forceSkeleton"了事。

### 2.5 初步设想 §9.6 的奖励缺两项（另有一项被 §1.1 吃掉）

初步设想 §9.6 定了四条：**基础**（等同敌袭房基准金币）、**提前**、**收集**、**无伤**。

| 来源 | 现状 |
|---|---|
| 基础 | 由 `onRoomCleared → settleRoomGold` 发 —— 现在被 §1.1 漏接了，修完自动回来 |
| 提前 | ✅ `unlockCollapse`：`remaining × 2` |
| 动态 · 收集 | ❌ 超过 need 的部分，每颗额外金币 |
| 动态 · 无伤 | ❌ 全程未掉落 → 额外 1 颗普通魂晶 |

`C.stats.falls` 已经在记，后两项都只是几行的事。

顺带核对初步设想 §9.6 里守点 / 限时的草案：

- 限时：`ceil(left/1000)*3 + 击杀*2` —— **与文档一致**。
- 守点：现在是 `10 + floor*2 + (血量>70% ? 10 : 0)`。文档写的是「基准 + 剩余时间 × 系数 + 血量保留」，但守点是累加式、没有「剩余时间」这个概念，所以实际换成了固定值 + 层数 —— 这是合理改写，建议回写文档，别让两处对不上。

### 2.6 机制保底可能整层失效

`pickMechanic`（12861）：

```
if (this.floor % 5 === 0 && node.col === 2 && !(this._floorMechanicCount > 0)) { ... }
```

- **col2 那一间如果是非战斗房（宝箱 / 祭坛 / 商店 / 休整 / 事件），保底直接失效** —— `pickMechanic` 开头就先 `return null` 了，走不到保底那行；
- 保底只在这一处检查。col2 之后如果还是没出现机制房，这一层就整层没有。

> 注意：分叉**不会**造成漏保底。`planFromRooms` 给同一列的两个候选的是同一个 col 号，所以玩家走哪条支路都满足 `node.col === 2`。

**建议**：改成「进层时掷一次『本层要不要保底』，要的话本层第一个战斗房强制挂」——把条件从「房间坐标」挪到「层」。

### 2.7 回退开关只做了一半

施工清单 §1.4「所有结构性改动都要有可回退的开关」；施工清单 §4.3 要求单向平台 / 三色 / 读条各自独立；施工清单 §5.3 要求踩头弹跳独立。

现状只有 `skeletonMode` 与 `setMechanicEnabled(name,on)`。单向平台、三色、读条、踩头都没有开关，出问题只能改代码。

**建议**：加一个 `setRhythmEnabled(name, on)` / `setCrystalMode(name, on)`，或者统一成 `API.setToggles({oneWay:true, tricolor:true, channel:true, stomp:true})`，默认全开。成本很低，救急时值钱。

### 2.8 守点圈没有 HUD 约束（手机上会压进 HUD / 文字出屏）

`startHold()`（12924）的选点逻辑是「取最高的那段平台」，然后 `y = spot.y - 6`，圈半径写死 `r = 72`，进度文字在 `y - 84`。**全程没有 `hudSafeTop()` 约束**（双层骨架反而有）。

实测（H=609，HUD 安全顶 197，两次不同选点）：

```
第 1 次：守点圈 y=277 r=72 → 顶边 205，文字 y=193   ← 文字已经在 HUD 区里
第 2 次：守点圈 y=224      → 顶边 152，整圈压进 HUD
```

两次差 53px 是因为平台位置是随机的 —— 也就是说「压不压 HUD」本身就是抽签。

按 `hudSafeTop()` 自己的注释，短屏 H≈360 时安全顶到 157（屏高 44%），而平台带是 50~154 —— 也就是**整条平台带都在 HUD 层里**。所以 360 高的手机上：

- 圈中心 ≈ 24~128，半径 72 → 圈有一半在屏幕外 / HUD 后面
- 文字 y ≈ -60~44 → **直接出屏**

依据：施工清单 §9.1「不出现出屏、压 HUD」、§9.3「提示位置不能遮挡血条 / 遗物栏」。

**建议**：不要用「夹 y」的写法 —— 把圈往下夹就等于把它从平台上挪走，和「圈在高处平台上成立」（施工清单 §7.3）冲突。正确做法是**按高度过滤候选平台**：

```
候选 = perches.filter(p => p.y >= hudSafeTop() + r + 90)   // 90 给文字留位
选点 = 候选里最高的 || perches 里最低的 || 地面兜底
```

这样有合格的高台就用高台，没有就退到低台、再退地面，三种情况都不出屏。顺带把 `r` 改成按 `H` 取比例（见 §2.10）。

### 2.9 矮屏上双层直接归零，35% 的分布只在桌面成立

`buildDoubleSkeleton()`：`deckY = max(groundY - 210, hudSafeTop + 44)`，再要求 `groundY - deckY >= 110`。

净空 = `groundY - max(groundY-210, hudSafeTop+44)`，所以只要 `groundY - hudSafeTop - 44 < 110` 就必然降级：

| 视口高 H | groundY | deckY | 净空 | 结果 |
|---|---|---|---|---|
| 360（推算） | 264 | 201 | **63** | 降级为平厅 |
| 420（推算） | 324 | 204 | 120 | 成立（玩家 46 高，头顶只剩 74） |
| 609（实测） | 513 | 303 | 210 | 成立 |

按 `hudSafeTop ≈ 157` 反推，**H 低于约 407 就再也出不了双层**。实测（H=349，n=600/档）：第 6/16/25 层的双层全部是 **0%**，断桥仍有 17~26%。也就是说手机横屏上双层房间**不是稀有，是根本不存在**，全部静默变成平厅。降级本身是对的（宁可平地也不给一个不可玩的房间），但：

- 施工清单 §6.1 验收写「第 16 层后占比 35% ± 5%」，这个数只在桌面成立；
- 玩家在手机上永远见不到双层，等于少了一整种骨架。

**建议**（二选一）：

- **A. 放宽约束**：净空下限从 110 降到 ~90（玩家 46 + 44 头顶），同时把 `hudSafeTop + 44` 换成平厅平台在用的 `H * 0.14`。理由：平厅平台本来就在 HUD 层里，靠相机纵向跟随补偿；双层没理由用更严的尺子。
- **B. 接受降级**：在两份文档里写明「手机端双层降级为平厅」，把施工清单 §6.1 的 35% 标注成「桌面视口」。

### 2.10 新元素尺寸没跟着视口走

施工清单 §9.1 要求「按视口比例自适应，不写死像素」。现在：

| 元素 | 尺寸 | 说明 |
|---|---|---|
| 守点圈 | `r = 72` 固定 | 同一间房在 360 和 720 上占屏比例差一倍，判定宽严也跟着变 |
| 魂晶 | 13×13 固定 | 可接受（与主角 48 同级），但小屏上相对更大 |
| 门上符文 | 12×14、间距 7 固定 | 贴着施工清单 §9.3「不低于 12px」的下限 |
| 塌陷预警 | 高度 72 固定 | 短屏上占 20% 屏高，偏厚 |

**建议**：至少把 `r` 和符文尺寸按 `H / 720` 夹一个 0.8~1.2 的系数，其余可以不动（游戏本体本来就是固定像素风格，强行全比例化反而破坏观感）。

### 2.11 触屏摇杆下推不触发地面防御

- `updateGuard`（10005）只读 `keys.guard / guard2 / ti.guardHeld`，**不读 `ti.downHeld`**。
- 所以键鼠上「地面按下 = 防御」，触屏上摇杆下推只负责加速下坠，防御只能按专门的盾键。
- 施工清单 §4.1 第 2 条写的是「地面按下 = 防御 …… 触屏摇杆向下推即可」。

**建议**：确认这是有意的（触屏有独立盾键，避免推摇杆误防御）。如果是，回写文档；如果不是，把 `ti.downHeld` 加进 `updateGuard` 的 held 判断，并注意和「下推=下坠」的互斥（空中下坠、地面防御，本来就不冲突）。

### 2.12 样板房的名字漏进了正式局

「塌陷回廊」是**样板房间 / 预览页**的名字（`其他/塌陷回廊预览.html`），不是游戏里的机制名。正式局里这个机制叫**塌陷**，和其他两个同一套写法：HUD 显示「房间:敌袭 · 塌陷」。

但代码里有三处把样板房的名字写进了正式局：

| 位置 | 现在 | 应该是 |
|---|---|---|
| `refreshHud` 的 `this.collapse` 分支（11810） | `'房间:塌陷回廊'`（正式局也是这句） | 预览页保留「塌陷回廊 · 样板房」；正式局走 `'房间:' + 房型名 + ' · 塌陷'`（与守点/限时同一条路径，`MECHANIC.names.collapse` 本来就是「塌陷」） |

### 2.13 起点房会抽到双层 / 断桥

`pickSkeleton` 只排除了三种：`floor <= 1`、层主房、非战斗房。**`start` 房不在排除名单里**（`nonCombatRoom` 也不含 start，因为它有敌人）。

所以第 2 层以后，玩家进层的第一间房可能就是一个双层或断桥：

```
实测 floor=20 的 start 房：骨架 = double
```

而 `pickMechanic` 里明确写了 `node.type === 'start'` → 不挂机制。同一个起点房，机制排除、骨架不排除 —— 这是两处判断不一致。

**建议**：`pickSkeleton` 里补上 `params.roomType === 'start'` → 返回 `'flat'`。理由：起点房是进层的缓冲房，只有 1~3 只杂兵，放个坑或上层没有玩法收益，反而会让"刚进层就被迫处理地形"。

## 4. 小问题（随手改）

1. **版本号不统一**：主界面 `v2.9.0`、更新日志 `version:'2.9'`、README 里「两套版本共存」那句还写「2.8（2D 实时）」。
2. **「第 2 层前不挂」文案差一层**：README 与更新日志都这么写，代码是 `floor >= 3`（第 3 层起）。
3. **`startHold` 开场播 `sfx('doorUnlock')`**，听起来像门已经开了，建议换个「机关启动」类的音。
4. **中途存档丢机制**：`checkpointState()` 不带 `mechanic`，中途退出再进，这间房会变回普通房。和「这个房间重来」的表述有出入。
5. **深渊魂晶只强化场上已有的怪**：`empowerRoomEnemies()` 不作用于之后刷出来的怪，塌陷 / 守点房会明显（那边是持续刷怪）。
6. **同段多颗钥匙会重叠**：`collapseFallGroup` → `relocateCollapseKey` 一律抛到 `next.x0 + 60~110`，同段两颗会叠在一个点。
7. **双层房 `platformSpots` 是空的**：`buildDoubleSkeleton` 不写 `platformSpots`，调试面板 / 分布统计会把双层房记成「0 段平台」。
8. **`spawnDeckSegment` 会吃掉零头**：`len = floor((x1-x0)/64)`，上层地板比设计短 0~63px，连通口看起来比 128 略宽。
9. **精英 / 镜像房挂机制会吃掉原本的怪**：`collapse` / `hold` 会设 `node.noEnemies = true`，精英房的精英、镜像房的镜像怪都没了。而且修完 §1.1 之后还有连带问题——`onRoomCleared` 里 `if (roomType === 'elite') s._pendingRelic = '精英遗物'`，于是会变成「**没打精英，照发精英遗物**」。建议 `pickMechanic` 里排除 `elite` / `mirror`（镜像房尤其该排除：它的意义就是打自己）。
10. **`buildDebugRoom` 的 `previewMode` 不复位**：从主游戏调 `startDebugRoom` 之后，`nextFloor` 会走「结算本局」而不是开地图。只在调试路径上，但容易踩。
11. **预览页把难度默认值抄了一份**：`其他/塌陷回廊预览.html` 的 `DIFF_DEFAULTS` 是 `MECH_DIFF` 的手抄版，改引擎不改页面就会对不上。建议引擎加一个 `API.getMechanicDefaults()`，页面直接读。
12. **`startCollapse` 与 `buildFlatSkeleton` 都清一次平台**：`_noPlatforms` 已经让平厅不建平台，`startCollapse` 里又销毁一遍。无害，但两处都在做同一件事，容易让人以为其中一处可以删。

### 5.1 骨架 / 机制的实际出现比例

**先说口径**：这两类东西有两套完全不同的分母，混着说会差两三倍。

- **口径 A：每个"能抽骨架的战斗房"** —— 设计文档里写的 40/35/25、15/10/10 都是这个口径
- **口径 B：每层实际走进的所有房间** —— 玩家体感是这个口径（含非战斗房、层主房）

#### 口径 A（实测，n=600~4000/档）

| 层数 | 平厅 | 双层 | 断桥 |
|---|---|---|---|
| 1 | 100% | 0 | 0 |
| 2~5 | 73~75% | 25~27% | 0 |
| 6~15 | 48~50% | 30~32% | 20~21% |
| 16~25 | 38~46% | 30~36% | 24~26% |

（目标是 40/35/25；25 层实测 37.7 / 36.2 / 26.2 基本吻合，16 层那次 46.2 / 30.0 / 23.8 偏低 —— n=600 的抽样噪声，不构成偏差。）

机制（战斗房内，第 3 层起）：

| 塌陷 | 守点 | 限时 | 无机制 |
|---|---|---|---|
| 14.2~15.8% | 9.1~10.8% | 8.8~10.4% | 64~67% |

第 2 层及以前 **0%**（`MECHANIC.minFloor = 3`）。

#### 口径 B（推算，按真实房间序列）

每层房间数 = `4 + min(2, 层数-1)` → **第 3 层起每层 6 间**（5 普通 + 1 层主）。
普通房在 8 种类型里**均匀**抽（敌袭 / 镜像 / 精英 / 休整 / 宝箱 / 商店 / 事件 / 祭坛），其中只有 3 种是战斗房 → **37.5%**；中间列还有一个支线候选（池子偏敌袭），按「支线被选一半」估算，玩家实际走进的约 **42~44%** 是战斗房。

非战斗房和层主房固定平厅、不挂机制，所以按全部房间算：

| 项 | 每层 | 占全部房间 |
|---|---|---|
| 平厅 | ≈ 4.7 间 | **≈ 79%** |
| 双层 | ≈ 0.74 间 | **≈ 12%** |
| 断桥 | ≈ 0.53 间 | **≈ 9%** |
| 机制房（任意） | **≈ 0.74 间** | **≈ 12%** |
| 　其中：塌陷房 | ≈ 0.32 间 | ≈ 5% |
| 　其中：守点 / 限时 | 各 ≈ 0.21 间 | 各 ≈ 3.5% |

> 表中前三行是**骨架轴**（平厅 4.7 + 双层 0.74 + 断桥 0.53 ≈ 6 间，可相加）；后三行是**机制轴**，和骨架是交叉关系，**不要和上面相加**。

**结论：每层平均不到 1 间机制房（约 0.74 间）** —— 平均下来大约每 1.4 层才遇到一间，大多数楼层一间都碰不到。

> 这不是 bug，是"35% 只作用在战斗房上、而战斗房只占 4 成"的算术结果。但如果 2.9 的目标是"让房间有清怪以外的动词"被玩家明显感知到，12% 偏低 —— 要么提挂载率，要么降低非战斗房占比，要么让机制也能挂在部分非战斗房上（比如宝箱房塌陷，拿了就跑）。

#### 手机端（H=349，实测）

| 骨架 | 平厅 | 双层 | 断桥 |
|---|---|---|---|
| 第 6 层 | 82.7% | **0%** | 17.3% |
| 第 16 层 | 74.7% | **0%** | 25.3% |
| 第 25 层 | 74.2% | **0%** | 25.8% |
