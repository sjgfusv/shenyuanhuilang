# 深渊回廊 2.9 施工清单

> **定位**：施工方案，不是开工记录。
> **依据**：`其他/2.9版本初步设想.md`（v7）。设计论证、取舍理由、实测数据都在那份文档里，本文不重复。
> **本文只回答三件事**：做什么 · 什么顺序 · 怎么算做完。
> **不含代码示例** —— 只写改动点、约束、验收口径。

---

## 0. 使用说明

- 施工顺序**不可乱**。每个阶段都写了「为什么排在这」，理由是依赖关系或归因需要，不是个人偏好。
- 每个阶段结束必须**独立可交付**：能玩、能测、能回退。不要出现「做到一半整个游戏不能玩」的状态。
- 验收标准里的数字都是**可测的**。凡是写不出测法的，说明这个需求还没想清楚，回头改设计而不是硬做。

---

## 1. 施工总则

### 1.1 五条不变量（任何阶段都不能破）

| # | 不变量 | 说明 |
|---|---|---|
| 1 | **老版 2.6 永远可玩** | 侧边栏切过去就是一个能跑完的 2.6，不依赖 2.9 任何改动 |
| 2 | **旧存档不丢** | 2.7 命名空间（`abyss27_*`）的存档能被 2.9 读入 |
| 3 | **降级链不断** | WebGL → Canvas → 说明面板，三条路径都还要能起 |
| 4 | **手机可玩** | 任意横屏尺寸下所有新元素按比例自适应：可见、可操作、不压 HUD |
| 5 | **图鉴不说谎** | 新房间/新机制进图鉴，说明文字从运行时代码读，不另写一份 |

### 1.2 2.9 的边界（明确不做）

**2.9 只改地形填充，不动空间模型。**

| 不动 | 原因 |
|---|---|
| 出口位置 | 一改就要动传送门坐标、触发判定、相机取景、开门条件 |
| 相机 bounds / follow | 纵向房间的前提，属于 3.0 |
| `groundY` 的含义 | 单层地面是全局假设，动了牵连太广 |
| 竖井 / 坠落井 / 蹬墙跳 / 钩爪 / 搬运 | 全部 3.0 |

> 判断标准很简单：**如果一个改动需要「出口换个位置」或者「相机要跟 y 轴」，它就不属于 2.9。**

### 1.3 三条硬红线

| 红线 | 出处 | 说明 |
|---|---|---|
| 前摇 ≥ 200ms | 完美闪避窗口固定 150ms | 压到窗口附近这一击就变成抽奖，不是变强是变坏 |
| 掉落伤害 ≤ 12% 最大生命 | 已拍板 | 按难度缩放，简单 4% / 普通 7% / 困难 10% / 地狱 12% |
| 不新增 HUD 元素 | 画面已经够挤 | 新信息优先用「场景内元素 + 飘字」承载 |

### 1.4 每个阶段都必须带开关

所有结构性改动都要有一个可回退的开关（本地常量或调试面板项即可），**默认值可以指向新逻辑，但旧逻辑必须还能跑**。

理由：骨架和怪物节奏都是全局改动，出问题时你需要能**当场降级**，而不是回滚一整个提交。

## 2. 施工顺序总览

```
P0 结构地基        无行为变化，只把「可替换的壳」搭好
 ↓
P1 平台与魂晶      单向平台 / 加速下坠 / 魂晶降频三色读条
 ↓
P2 战斗节奏        前摇不重置 + 霸体 + 近战怪对空 + 踩头弹跳（必须同批）
 ↓
P3 骨架            双层 → 断桥（逐个上，逐个验收）
 ↓
P4 机制            预览页样板房 → 塌陷 → 守点 → 限时
 ↓
P5 投放与收尾      权重接入 / 图鉴 / 更新日志 / 全量回归
```

### 2.1 为什么是这个顺序

| 顺序 | 理由 |
|---|---|
| **P0 最先** | 先搭壳再塞玩法。否则你会一边改生成器一边改玩法，出问题分不清是谁的锅 |
| **P1 在 P2 前** | 魂晶和平台是「不改变战斗空间感」的改动，先做掉可以单独验证 |
| **P2 在 P3 前** | **先调怪，再改地形。** 反过来的话，玩家抱怨变难/变简单，你无法归因是地形还是怪 |
| **P3 在 P4 前** | 塌陷机制需要「地面分段」，而分段是断桥的变体 —— 断桥做完，塌陷才顺 |
| **P4 里样板最先** | 先做一个独立预览页、玩 20 遍，再参数化。反过来做就是「先有系统再找玩法」，那正是现在生成器像装饰的原因 |

### 2.2 一个必须成对上线的组合

**踩头弹跳（P2）必须和近战怪对空（P2）同一批上线。**

只上踩头不上对空，玩家可以反复滞空，而 `chaser` / `charger` / `bulwark` 完全摸不到人 —— 这会变成比现在更严重的无解打法。这两个不能拆开验收。

## 3. P0 结构地基

**目标**：把「地形生成」和「房间完成判定」抽成可替换结构，**但行为零变化**。

**为什么排第一**：这是唯一一个「做完之后玩家感知不到任何区别」的阶段。它的价值是让后面所有改动都有一个干净的落点，且随时可回退。

### 3.1 任务

| # | 任务 | 说明 |
|---|---|---|
| 1 | 把平台生成拆成「骨架选择」+「骨架实现」两层 | 骨架选择读层数/视口/房间类型；骨架实现目前只写「平厅」一种，内部逻辑与现有随机撒点等价 |
| 2 | 新增骨架参数入口 | 层数、视口高宽、房间类型、房间宽度。平厅骨架暂时忽略大部分参数 |
| 3 | 房间完成判定抽成统一目标结构 | 支持 `arrive` / `collect` / `hold` / `timed` / `clear` 五种类型，**目前只实现 `clear`** |
| 4 | 开门逻辑改为读目标结果 | 不再直接读「敌人数量是否为 0」 |
| 5 | 加 `skeletonMode` 开关 | `legacy` = 旧生成器，`skeleton` = 新骨架系统。默认 `skeleton`，但平厅实现必须与旧路径结果同分布 |
| 6 | 清理路径覆盖新增对象 | 出房/重开时必须把骨架生成的所有对象清干净，不能有残留 |

### 3.2 验收

| 项 | 标准 | 怎么测 |
|---|---|---|
| 行为无变化 | 连续 20 局，平台数量与高度分布与改造前统计一致 | 用开发者模式导出每房平台坐标，对比改造前后各 20 局的分布 |
| 回归全绿 | `测试/` 下所有脚本 100% 通过 | 直接跑 |
| 帧时间不升 | 与改造前持平（基线 1.16ms/帧，7 敌人） | 压力场景实测 |
| 手机布局不变 | 同一视口下房间观感与改造前一致 | 抽 2~3 档高度截图对比 |
| 开关有效 | 切到 `legacy` 后完全回到旧行为 | 手动切换 + 跑一遍回归 |
| 无残留 | 连续进出房间 30 次，显示对象与纹理数量不增长 | 开发者面板计数 |

### 3.3 回退

`skeletonMode = 'legacy'` 即完全回到 2.8 行为。这一阶段不需要回滚代码。

## 4. P1 平台与魂晶

**目标**：让「平台」第一次变得可穿过、可下落，让「魂晶」从地板掉落变成值得绕路的目标。

**为什么排在 P2 前**：这一阶段**不改变战斗空间感**（不碰怪、不碰跳跃高度、不碰踩头），可以独立验证。魂晶改动是纯数值 + 表现层，风险最低。

### 4.1 任务

| # | 任务 | 说明 |
|---|---|---|
| 1 | 单向平台 | 从下往上能穿过，从上方能踩住。注意与现有「平台是实心碰撞体」的假设冲突，需要逐处排查依赖 |
| 2 | 加速下坠穿平台 | 加速下落并穿过单向平台，落到下一层。**输入复用「下」：空中按下 = 加速下坠，地面按下 = 防御** —— 两个状态互斥，触屏摇杆向下推即可，不需要新按钮 |
| 3 | 魂晶降频 | 从「每段平台 62%」改为「每房保底 1 颗 + 30% 概率额外 1 颗，上限 2 颗」 |
| 4 | 魂晶三色 | 蓝 / 深渊 / 腐化。**三色共用同一套显示对象，用 tint 区分，不要建三套纹理** |
| 5 | 读条拾取 | 见 §9.2 的触控适配结论 |
| 6 | 低血回血显性化 | 血量低于 60% 时魂晶变绿 + 提示文字改为「救命」+ 图鉴补一条 |
| 7 | 单颗收益上调 | 降频后单颗收益上调 50%~80%，避免经济缩水 |

### 4.2 验收

| 项 | 标准 | 怎么测 |
|---|---|---|
| 单向平台 | 从下往上跳不被顶住；从上落下能站稳 | 每个骨架各测 10 次 |
| 加速下坠 | 能穿过平台落到下一层，不会卡在平台内 | 双层场景测 |
| 魂晶频率 | 20 房平均 ≤ 1.5 颗，且每房至少 1 颗 | 开发者模式统计 |
| 三色可辨 | 三种颜色在最小视口（高度 360 左右）下仍可区分 | 缩到最小截图 |
| 读条可打断 | 移动 / 受击 / 怪贴近都会取消读条 | 逐项测 |
| 低血显性化 | 血量 <60% 时外观明显不同，玩家不看图鉴也能感知 | 3 人盲测（给截图问「这颗魂晶有什么不一样」） |
| 经济不崩 | 单局总收益与 2.8 相比波动 ≤ 15% | 10 局平均 |

### 4.3 回退

单向平台、三色、读条各自独立开关。魂晶频率是一个常量，改回去即可。

---

## 5. P2 战斗节奏（怪 + 空中）

**目标**：把怪从「沙包」改回「对手」，同时让「踩头」成立。

**为什么必须一起做**：见 §2.2。这两个改动互为前提 —— 怪能出手，踩头才有意义；怪能对空，踩头才不会变成无解。

### 5.1 任务

| # | 任务 | 说明 |
|---|---|---|
| 1 | 前摇计时器不因受击重置 | 受击只进硬直，前摇计时继续走；硬直结束时若已超时，立刻出手 |
| 2 | 前摇后段霸体 | 起手动作最后约 40% 不可打断 |
| 3 | `chaser` 跳跃扑击 | 玩家滞空时起跳扑一次，前摇约 300ms 可闪 |
| 4 | `charger` 冲锋纵向加高 | 不再只能撞到地面高度的人 |
| 5 | 踩头弹跳 | 从上方落下踩到敌人头顶 → 弹起 + 重置空中攻击 |
| 6 | 受击硬直递减（观察后再上） | 连续受击 150 → 110 → 80 → 60 → 0。**先不做，等 1~5 验收完再评估** |

### 5.2 验收

| 项 | 标准 | 怎么测 |
|---|---|---|
| 怪能出手 | 单挑黑暗爪牙时，玩家不闪不避，怪必须能打中至少 1 次 | 固定场景测 10 次 |
| 不被永久压制 | 玩家连续攻击时，怪仍能出手 | 同上 |
| 前摇不破线 | 所有敌人前摇 ≥ 200ms（含难度缩放后） | 开发者模式导出全部敌人数值 |
| 踩头可用 | 踩头能稳定触发，落地/弹起判定不吞输入 | 连续 20 次，成功率 100% |
| 踩头不无敌 | 踩头后立刻有对空威胁，不能站着刷 | 场景：2 只 chaser + 1 只 shooter，测 10 次 |
| 难度可通 | 普通难度前 10 层可正常推进，不出现「怪打不死」或「被秒」 | 完整试玩 5 局 |
| 简单难度保留沙包感 | 简单难度下仍能轻松压制（这是给新手的） | 试玩 3 局 |

### 5.3 回退

- 前摇不重置、霸体：按难度分级开关，简单难度可关。
- 踩头弹跳：独立开关，关掉即回到 2.8。

### 5.4 风险

这一阶段是 2.9 里**唯一会明显改变全局手感**的改动。如果试玩反馈「怪变太凶」，优先调霸体比例（40% → 25%），不要动 200ms 下限。

## 6. P3 骨架

**目标**：让 60% 的战斗房间不再是平地。

**为什么排在 P2 后**：地形会改变战斗空间，必须在战斗节奏稳定之后再上，否则两个变量一起动无法归因。

### 6.1 P3.1 双层

| # | 任务 |
|---|---|
| 1 | 双层骨架生成：上层实体地板 + 1~2 个连通口，位置参数化 |
| 2 | 出口仍在地面右端（**不改出口位置**，这是 2.9 的边界） |
| 3 | 上层放置远程怪（复用现有高台怪逻辑） |
| 4 | 上下层净空校验：沿用现有「水平投影重叠则高度必须拉开」的规则 |
| 5 | 玩家可达性校验：上层高度必须在满蓄力跳跃范围内 |

**验收**

| 项 | 标准 |
|---|---|
| 可达 | 满蓄力能稳定上到上层（20 次无失败） |
| 不卡怪 | 不会有怪卡在两层之间（打不到也出不来） |
| 不压 HUD | 最小视口高度下上层仍完全可见，不进入 HUD 层 |
| 生成率 | 第 16 层后占比 35% ± 5% |
| 帧时间 | 不高于 P2 结束时 |

### 6.2 P3.2 断桥

| # | 任务 |
|---|---|
| 1 | 地面分段生成：1~2 处缺口，缺口下是坑 |
| 2 | 掉落判定：掉出下边界 → 扣血 + 传回最近安全点 |
| 3 | 缺口视觉：与地面同材质，用遮罩或分段表现，**不要新增纹理** |
| 4 | 怪的落点修正：怪不能生成在缺口上方 |

**验收**

| 项 | 标准 |
|---|---|
| 掉落有反馈 | 掉下去扣血、有音效、传回位置合理（不往回送） |
| 跳跃可过 | 缺口宽度在「轻点跳」范围内（不能逼玩家满蓄力） |
| 不卡怪 | 怪不会掉进坑里卡住导致房间清不空 |
| 生成率 | 第 16 层后占比 25% ± 5% |
| 手机 | 缺口在最小视口下清晰可辨 |

### 6.3 回退

每个骨架独立开关，可单独关掉回到平厅。生成率常量可调。

## 7. P4 机制

**目标**：让房间有「清怪」以外的动词。

**为什么按这个顺序**：样板房间必须最先做，而且必须**独立于主流程**。这是整套设计的验证点 —— 如果这一个房间不好玩，后面两个机制不用做了。

### 7.1 P4.0 样板房间：独立预览页（不进主游戏）

**做法：先做 `其他/塌陷回廊预览.html`，单独一个页面只跑这一个房间。**

这与项目现有的 `其他/开始界面样式预览.html`、`其他/角色形象预览.html`、`其他/遗物图标预览.html` 是同一个惯例 —— **调参快、不污染主流程、能反复重开**。

为什么不直接塞进主游戏：进了主流程就变成「打一层、死一次、重开、再走到第 5 层」，一次验证要好几分钟。而样板房间需要**反复玩 20 遍以上**，必须能一键重开。

#### 任务

| # | 任务 | 说明 |
|---|---|---|
| 1 | 新建 `其他/塌陷回廊预览.html` | 复用 `vendor/phaser.min.js` + 现有战斗引擎，跳过楼层/房间流程直接起一个房间 |
| 2 | 引擎加一个「调试单房间」入口 | 允许指定房间类型与骨架，不走正常的房间序列（这是 P4.0 唯一允许改主引擎的地方） |
| 3 | 地面分段 + 逐段塌陷 + 预警 | 按初步设想 §9.3 的时间轴 |
| 4 | 出口锁 + 3 个符文凹槽 + 集齐开门 | 按初步设想 §9.2 的「出口锁的具体实现」 |
| 5 | 魂晶作为钥匙（需求按层数变，标准档 3 颗 / 投放 5 颗） | 魂晶位置：3 颗在平台上，2 颗在半空 |
| 6 | 掉落传送（前沿 + 1） | 按初步设想 §9.4 |
| 7 | 强制解锁兜底（**最后一段**预警时，段数随层数变） | |
| 8 | 被困脱困（提示 + 崩解兜底） | 按施工清单 §9.2 ② |
| 9 | 预览页侧栏：一键重开 / 参数调节 / 实时计时 / 导出数据 | 见下两节 |

#### 预览页必须带的调试能力

| 控件 | 用途 |
|---|---|
| **一键重开**（`R`） | 核心。一次验证要在 30 秒内完成，重开不能超过 1 秒 |
| 段数 / 塌陷间隔 / 魂晶需求 三个滑杆 | 现场调参，不用改代码 |
| 通关计时（实时） | 玩的时候就能看到当前用时 |
| **导出数据** | 核心。20 遍玩完要能一眼看出该调什么，见下节 |

> 移动端适配不在这里做视口切换 —— 浏览器自带的设备仿真就够用，
> 自己再做一个切换器是重复造轮子，还容易和真实的 devicePixelRatio 不一致。

#### 导出什么数据（这一节决定预览页有没有用）

只记「玩了多久」没用。**要记的是能反推参数的那几个量。**

**每局结束自动记一条：**

| 字段 | 说明 | 用来判断 |
|---|---|---|
| 通关时间 | 从进房到出口开启 | 节奏是否成立（目标 20~35s） |
| 掉落次数 | 这局掉了几次坑 | 塌陷节奏是否过密 |
| 魂晶收集 / 需求 | 如 3/3、2/3 | 门槛是否合理 |
| 是否强制解锁 | 靠最后一段兜底开的门 | **最关键** —— 高了说明集不齐 |
| 被困时长 | 在平台上等崩解的时间 | 平台分布是否合理 |
| 受伤总量 | 全程掉血 | 整体压力 |
| 击杀数 | | 怪是否只是干扰 |
| 读条被打断次数 | | 怪的位置是否有意义 |
| 出口开启时的塌陷段数 | 如「第 5 段时开的门」 | 玩家平均推进速度 |

**页面底部常驻累积统计：**

| 统计 | 说明 |
|---|---|
| 局数 / 平均时间 / 最快 / 最慢 | 看稳定性 |
| 强制解锁率 | 兜底被触发的比例 |
| 掉落率（有掉落的局占比） | 压力是否合适 |
| 平均收集数 | 魂晶位置是否够得着 |
| 被困率 | 平台是否把人困住 |

**导出方式**：一个按钮，导出 JSON（含参数快照 + 每局记录 + 汇总），同时支持复制到剪贴板（手机上也能取出来）。

#### 用导出的数据判断该调什么

这张表是预览页真正的价值所在 —— **它把「我觉得有点难」变成「强制解锁率 40%，该降门槛」**。

| 指标 | 健康区间 | 偏离说明什么 | 该调什么 |
|---|---|---|---|
| 平均通关时间 | 20~35 秒 | 偏短=没压力，偏长=太拖 | 塌陷间隔 |
| **强制解锁率** | **< 20%** | 偏高=魂晶集不齐 | 降需求 或 加魂晶 或 放慢塌陷 |
| 掉落率 | 20%~50% | 偏低=没威胁，偏高=太苛刻 | 塌陷间隔 / 平台间距 |
| 平均收集数（共 5 颗） | 3.5~4.5 | 偏低=魂晶位置不合理 | 魂晶位置 / 读条时长 |
| 被困率 | < 10% | 偏高=平台把人困死 | 平台间距 / 增加连通 |
| 读条被打断次数 | 平均 1~3 次 | 为 0=怪没起作用，偏高=太烦 | 刷怪节奏 / 怪的距离 |

## 9. 移动端适配专项

> 这一节单独列，因为它是 2.9 最容易翻车的地方 —— 现有代码里所有的尺寸假设都是「横向 + 单层地面」，而新东西很容易在不经意间写死像素。

### 9.1 尺寸：按视口比例自适应，不针对具体机型

**先明确一条原则：不为某个具体尺寸做适配，只保证「任意尺寸下按比例自适应」。**

写死某个分辨率（比如「在 800×360 下正常」）是**面向结果编程** —— 那只是某台手机的形状，换个机型就崩。正确的做法是让公式本身自适应，于是任何尺寸都自然成立。

现有代码里 `spawnPlatforms` 的 `max(groundY - 350, H * 0.14)` 就是正面例子：它没有假设任何机型，而是拿视口高度算比例。**2.9 所有新元素都照这个思路来。**

| 项 | 要求 |
|---|---|
| 平台高度 | 用「离地可用高度」的比例算，不用固定 px |
| 平台段数 | 按可用高度分档，高度不足时自动降一档 |
| 缺口宽度 | 按角色跳跃能力算，不按像素 |
| 魂晶尺寸 | 按视口缩放，缩到最小也要能一眼看到 |
| 门上的符文凹槽 | 同上，不能小到看不清 |

**判定标准**：视口高度从 360 拉到 720、宽度从 640 拉到 1280，所有新元素都要「看起来是同一张图缩小的」，不出现出屏、压 HUD、或小到看不清 —— **中间不能有某个尺寸突然崩掉**。

> 测试时抽几档看一眼是采样手段，不是验收标准。标准是「自适应」，不是「某个尺寸下好看」。

### 9.2 触控：两个新交互必须先解决

**① 读条拾取 —— 已定案：停留触发**

初步设想 §7.4 原本写的是「按住 0.6 秒」。这在键鼠上没问题，在触屏上是**双指冲突** —— 玩家要一边推摇杆一边按住拾取，手机上是两根手指，很别扭。

**定案：改成「停留触发」，不按任何键。**

| 规则 | 说明 |
|---|---|
| 触发 | 靠近魂晶后**站住不动 0.2 秒**开始读条 |
| 打断 | 移动 / 受击 / 怪进入 60px 内 |
| 不触发 | 快速跑过（不停留）不会开始读条 —— 这就是「不拿」的表达 |
| 时长 | 0.6 秒 |

**附带解决了一个设计问题**：玩家不想拿腐化魂晶时，直接跑过去就行，不需要额外的「取消拾取」操作。选择从「按不按」变成「停不停」，更自然，而且键鼠与触屏完全一致。

> 实现要点：判定用「位置变化速度 < 阈值持续 0.2 秒」，不要用「没有输入」—— 摇杆回中但有惯性时会误判。

**② 跳崖脱困 —— 不需要新按键**

初步设想 §9.8 原本写的是「按 ↓ 跳下」。查过触控布局后，这个方案有问题：**摇杆向下推大概率已经对应「防御」**，再挂一个「跳下」会冲突。

**但想清楚之后发现：根本不需要新操作。**

> 玩家从平台边缘走出去就会掉下去 —— **「跳下」这件事本来就能做，只是玩家不知道掉下去是好事。**

所以问题不是「缺一个按键」，是「缺一个认知」。解法是把认知补上：

| 时间线 | 事件 |
|---|---|
| 被困第 0 秒 | 平台边缘出现微光（暗示「这边可以跳」） |
| 被困第 3 秒 | 弹提示：**「深渊会把你送回前方 · 跳下去（−12% 生命）」** |
| 被困第 8 秒 | 平台开始崩解：抖动 + 裂缝 + 碎石 |
| 崩解后 2 秒 | 平台碎裂，玩家自动掉落 → 传送到前沿 + 1，**不扣血** |
| 崩解时 | 提示改为「深渊吞噬了这块地面」 |

**这个设计顺带解决了一个死锁**：低血被困时，主动跳可能摔死，所以给一条「等崩解」的路 —— **不扣血，但要等 10 秒且拿不到速度奖励**。

于是被困时玩家有一个真选择：

```
跳下去  → 立刻脱困，代价是血
等崩解  → 不扣血，代价是时间和奖励
```

> 注意区分：这不是「平台会崩」那个机制（初步设想 §9.8 里否掉过，因为它会让魂晶跟着消失）。这里的崩解**只在「被困 8 秒」这个极端条件下触发**，此时魂晶要么已经拿了、要么已经拿不到，不会造成额外损失。

**验收**：真机上只用拇指、不加任何新按钮，能完成「被困 → 跳下 → 传送」全过程。

## 10. 性能专项

### 10.1 基线

| 项 | 数值 |
|---|---|
| 现有压力场景 | 7 敌人持续攻击 ≈ 1.16ms/帧 |
| **2.9 红线** | **任何场景 < 2.0ms/帧** |
| 显示对象 | 长时间战斗后数量保持恒定（不增长） |

### 10.2 必须遵守的实现约束

| # | 约束 | 原因 |
|---|---|---|
| 1 | 地面分段**不要**变成 N 条 TileSprite | 现在是 1 次绘制，切成 N 段就是 N 次。用「整条 + 缺口遮罩」 |
| 2 | 魂晶三色**共用**显示对象 + tint | 建三套纹理等于三倍显存与三次纹理切换 |
| 3 | 平台碰撞体尽量复用，不要频繁 create/destroy | 现有 `platformTiles` 是即用即建，骨架切换时要走统一清理 |
| 4 | 骨架生成只在**进房时算一次** | 不能每帧计算布局 |
| 5 | 塌陷粒子复用现有 `spark()` | 不要新写一套粒子 |
| 6 | 塌陷的定时器统一管理 | 出房时必须全部清掉，否则回到主界面还在跑 |
| 7 | 新增音效走现有合成器 | 不引入素材文件，不新增 AudioContext |

### 10.3 压力场景（每个阶段都要跑）

| 场景 | 内容 |
|---|---|
| A | 7 敌人 + 平厅（基线对照） |
| B | 7 敌人 + 双层 |
| C | 7 敌人 + 断桥 |
| D | 3 敌人 + 塌陷（最高档 10 段全塌一遍） |
| E | 塌陷 + 双层（最坏组合） |
| F | 连续进出房间 30 次（查泄漏） |
