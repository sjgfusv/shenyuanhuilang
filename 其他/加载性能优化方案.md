# 深渊回廊 · 网页加载性能优化方案

> 起因：Netlify 线上版（`effervescent-puppy-941d9f.netlify.app`）在手机和电脑上打开都要等很久。
> 依据：线上 HAR 抓包（`effervescent-puppy-941d9f.netlify.app.har`）+ 本机现场实测。
> 核心承诺：**玩法、数值、存档、剧情、界面零改动。**

---

## 一、结论先行

慢的原因有两层，不要只盯着一层：

| 层次 | 问题 | 占比 | 现状 |
|---|---|---|---|
| **主因** | Netlify 的 CDN 到中国大陆只有 **约 30 KB/s** | 约 75% | 同一份 `phaser.min.js`，Netlify 要 36.8 秒，jsDelivr 只要 5.7 秒 |
| **放大器** | 首屏要下 **2.59 MB**，且 6 个脚本全部同步阻塞 | 约 25% | HAR 实测 `onLoad = 22.5 秒` |
| 次因 | 每次回访都重新验证，无 Service Worker | — | `cache-control: max-age=0, must-revalidate` |
| 次因 | `index.html` 用 `meta refresh` 跳转 | — | 白白多一次完整往返（实测 ~2.3 秒） |

**做完本方案的全部优化后：**

| 场景 | 现在 | 优化后（继续用 Netlify） | 优化后（换 Cloudflare Pages） |
|---|---|---|---|
| 首次打开（新玩家） | **22.5 秒** | **约 4 秒** | **约 0.5 秒** |
| 第二次打开（回访） | 约 20 秒 | **约 0.3 秒**（Service Worker 命中） | 约 0.3 秒 |

依据：首屏体积从 2587 KB 降到 417 KB（-84%），Netlify 开启 br 压缩后实际传输约 120 KB；30 KB/s → 4 秒，250 KB/s → 0.5 秒。

## 二、实测诊断

### 2.1 同一个文件、不同 CDN（本机实测，2026-09）

下载的都是 `phaser.min.js`，1,181,917 字节，内容完全相同：

| 来源 | 耗时 | 速度 | 相对倍数 |
|---|---|---|---|
| **你的 Netlify 站点** | **36.8 秒** | **32 KB/s** | 1× |
| jsDelivr CDN | 5.7 秒 | 208 KB/s | **6.5×** |
| unpkg CDN | 6.2 秒 | 192 KB/s | 6.0× |
| Cloudflare 测速端点 | 3.9 秒/MB | 253 KB/s | 7.9× |
| 对照组：百度 | — | TTFB 0.43 秒（正常） | — |

> 结论：**不是你的网络有问题，也不是手机的问题。** HAR 里的 UA 是 `Windows Chrome 109`，电脑上一样慢。
> 是 Netlify 的边缘节点到中国大陆这条链路只有 ~30 KB/s。

### 2.2 首屏到底在下什么

`主界面.html` 第 732–736 行，连着 5 个 `<script>`，**全部没有 `defer` / `async`**：

```html
<!-- 主界面.html 行 731-736 -->
<script src="vendor/phaser.min.js?v=20250907p"></script>   <!-- 1154 KB -->
<script src="角色形象.js?v=20250910r2"></script>            <!--   60 KB -->
<script src="战斗2D.js?v=202610210"></script>               <!--  545 KB -->
<script src="主程序.js?v=202610230"></script>               <!--  511 KB -->
<script src="经典2D.js?v=202610220"></script>               <!--  110 KB -->
```

加上 `<head>` 行 24 的 `AbyssAudio.js`（43 KB）和行 23 的 `主样式.css`（163 KB）：

| 文件 | 大小 | 占比 | HAR 实测耗时 |
|---|---|---|---|
| `vendor/phaser.min.js` | 1154 KB | 45% | **18.1 秒** |
| `战斗2D.js` | 545 KB | 21% | **13.8 秒** |
| `主程序.js` | 511 KB | 20% | **10.8 秒** |
| `经典2D.js` | 110 KB | 4% | 1.7 秒 |
| `角色形象.js` | 60 KB | 2% | 3.5 秒 |
| `AbyssAudio.js` | 43 KB | 2% | 0.7 秒 |
| `主样式.css` | 163 KB | 6% | （录制时已缓存） |
| **合计** | **2587 KB** | | |

浏览器解析到第 732 行就被 phaser 卡住，**必须等它下载完才能继续解析 HTML** —— 所以开始界面（星空 + "开始游戏"按钮）在 21 秒内根本没机会出现，`onLoad` 停在 22.5 秒。

### 2.3 为什么"每次"都慢

HAR 里全部 9 个请求的响应头都是：

```
cache-control: public,max-age=0,must-revalidate
```

这是 Netlify 对没有自定义头的静态文件的默认行为。有 ETag，所以回访会返回 304 而不是重下 —— **但每次仍要走一个完整往返**去问服务器"变了没"。在 1.3 秒 TTFB 的链路上，就是每次回访白等一两秒；一旦本地缓存被清（手机浏览器很常见），就要重下全部 2.59 MB。

加上项目里**没有 Service Worker**，PWA 只做了一半（有 `manifest.webmanifest`，没有离线缓存）。

### 2.4 `index.html` 的额外一跳

```html
<meta http-equiv="refresh" content="0; url=主界面.html" />
```

访问根域名 → 先下 `index.html`（TTFB 实测 1.34 秒）→ 再跳 `主界面.html`（TTFB 0.94 秒）。**多花约 2.3 秒纯等待**，白白浪费。

## 三、一个关键发现：首屏其实不需要 Phaser

这一节决定了方案能省多少。我逐项查了代码，结论是：

### 3.1 `主程序.js` 完全不依赖 Phaser

全项目搜索 `Phaser` 的出现次数：

| 文件 | 出现次数 |
|---|---|
| `战斗2D.js` | 87 |
| `经典2D.js` | 7（全部在注释里） |
| `角色形象.js` | 2 |
| `试炼程序.js` | 5（**这个文件根本没被 `主界面.html` 加载**） |
| **`主程序.js`** | **0** ← |

### 3.2 `主程序.js` 对 2D 引擎的引用全是"防御式"的

```js
// 主程序.js 行 2454
if (window.经典2D && window.经典2D.cheat) return window.经典2D.cheat;

// 主程序.js 行 433
if (!t2d || !t2d.enterLayoutEdit) {
    showToast('2D 模块未加载，无法打开布局编辑器');
    return;
}

// 主程序.js 行 11685
const e = window.战斗2D;
if (!e) return devLog('2D 引擎未加载');
```

而且我用正则扫过 **`主程序.js` 里没有任何一处在顶层（缩进 0）立即取用 `window.战斗2D / 经典2D / 试炼2D`** —— 全都是用户点击后才执行的函数体内部，并且已经写好了"引擎没加载"的降级提示。

> 代码作者（也就是你）当初就是按"引擎可能不在"来写的。这让延迟加载变得非常干净。

### 3.3 依赖顺序（必须保持）

```
AbyssAudio.js  →  window.AbyssAudio          （独立）
vendor/phaser.min.js → window.Phaser          （独立库）
角色形象.js     →  window.角色形象            （独立，但内部用到 Phaser.Api）
战斗2D.js      →  顶层就有 class BattleScene extends Phaser.Scene  ⚠️ 必须等 Phaser 就绪
                →  顶层 var A = global.角色形象                       ⚠️ 必须等 角色形象 就绪
经典2D.js      →  运行时依赖 主程序.js 的 window.经典2D内核
主程序.js      →  运行时（带防御检查）依赖上面全部
```

⚠️ **唯一硬约束**：`战斗2D.js` 顶层写着 `class BattleScene extends Phaser.Scene`，这是**脚本解析时**就求值的。所以 `phaser.min.js` 必须在 `战斗2D.js` **之前**执行完 —— 延迟加载时必须串行，不能并行。

### 3.4 于是首屏被拆成两份

| | 文件 | 压缩后 | 何时需要 |
|---|---|---|---|
| **首屏必需** | `主程序.js` | 305 KB | 立刻 |
| | `主样式.css` | 94 KB | 立刻 |
| | `AbyssAudio.js` | 18 KB | 立刻 |
| | **小计** | **417 KB** | |
| **可以晚点要** | `vendor/phaser.min.js` | 1154 KB | 进入 2D 战斗时 |
| | `战斗2D.js` | 247 KB | 进入 2D 战斗时 |
| | `经典2D.js` | 38 KB | 进入 2D 战斗时 |
| | `角色形象.js` | 28 KB | 进入 2D 战斗时 |
| | **小计** | **1467 KB** | |

**首屏 2587 KB → 417 KB，砍掉 84%。** 这就是"约 4 秒"的来源。

## 四、优化项清单（按风险从低到高）

### 🟢 A 级 · 完全不碰游戏代码

| # | 做什么 | 收益 | 风险 | 工作量 |
|---|---|---|---|---|
| A1 | 加 `_redirects`，把 `/` 直接 200 重写到 `主界面.html` | 省掉 2.3 秒白等 | 无 | 5 分钟 |
| A2 | 加 `_headers`，给带 `?v=` 的资源设长缓存 | 回访不再重新验证 | 见下方说明 | 10 分钟 |
| A3 | 加 Service Worker，预缓存全部资源 | **回访 20 秒 → 0.3 秒** | 见下方说明 | 1–2 小时 |
| A4 | **换托管到 Cloudflare Pages** | 30 KB/s → 250 KB/s，**8 倍** | 无 | 30 分钟（需你注册账号） |

**A1 具体做法** —— 新建 `_redirects`（Netlify 和 Cloudflare Pages 语法通用）：

```
/  /主界面.html  200
```

用 200 重写而不是 301 跳转：浏览器地址栏不变、不产生第二次请求，比 `meta refresh` 快一整个往返。同时把 `index.html` 从项目里删掉（或改成纯说明页）。

**A2 具体做法** —— 新建 `_headers`：

```
/*
  Cache-Control: public, max-age=0, must-revalidate

/*.js
  Cache-Control: public, max-age=31536000, immutable

/*.css
  Cache-Control: public, max-age=31536000, immutable

/vendor/*
  Cache-Control: public, max-age=31536000, immutable
```

> ⚠️ **这里有个必须遵守的纪律**：项目已经在用 `?v=202610230` 这种方式手动管理版本号，所以 `immutable` 是安全的 —— **但前提是你每次改完文件必须改版本号**。改了文件却没改 `?v=`，玩家会一直看到旧版。
> 如果觉得这个纪律容易忘，可以退一步，把 `immutable` 改成 `max-age=604800`（7 天），风险更小。

**A3 的 Service Worker 设计要点**：

- 用 **stale-while-revalidate** 策略：先给缓存里的版本（秒开），后台静默拉新版，下次进来就是新的。
- 缓存版本号写死在 `sw.js` 里（如 `const CACHE = 'abyss-v2.7.1'`），你每次发版改一次这个号 → 老缓存自动作废。
- `sw.js` 本身必须走网络（不能缓存），否则新 SW 永远装不上。
- 监听 `message` 事件支持"跳过等待"，配合页面提示"有新版本，点击刷新"。

**A3 的风险说明（重要，必须知道）**：
> Service Worker 是唯一会让**你自己**在发版后可能看到旧版本的优化项。这是所有 PWA 的通病，不是这个项目的 bug。上面第 2、4 点就是解药。如果你觉得这个心智负担不值得，可以只做 A1/A2/A4 —— 收益已经很大。

### 🟡 C 级 · 改加载时机，不改代码逻辑

| # | 做什么 | 收益 | 风险 |
|---|---|---|---|
| C1 | 给 6 个 `<script>` 加 `defer` | 开始界面**立刻**出现 | **极低**（见下） |
| C2 | 把 2D 四件套从首屏拆出去，文字界面阶段完全不加载 | 首屏 **-1467 KB（-84%）** | 低 |

**C1 为什么风险极低**：`defer` 脚本**严格按文档顺序执行**，所以现在的 `phaser → 角色形象 → 战斗2D → 主程序 → 经典2D` 顺序**完全不变**。唯一变化是 HTML 解析不再被阻塞 —— 星空开始界面会秒出，而不是白屏 21 秒。

`主程序.js` 的启动本来就挂在 `DOMContentLoaded`（行 9987、12519），`defer` 脚本在 `DOMContentLoaded` **之前**执行完，时序天然兼容。

**C1 的实际体感**：下载总量不变，但玩家**立刻看到东西**。这是"感知性能"最大的一笔。

#### C2 详解 —— 好消息：这条加载边界，你自己早就划好了

你问"能不能文字界面和 2D 分开加载"。答案是**能，而且这不是要新造的东西 —— 项目现在就是这么设计的**。

证据在 `经典2D.js` 第 102–118 行，你自己写的：

```js
/**
 * 现在该不该由宿主管画面
 * 选英雄 / 选增益 / 开始界面仍归内核 DOM；一旦进了房间就交给 2D。
 */
function shouldTakeOver() {
  var s = S();
  if (!s || !s.hero) return false;
  if (s.gameOver) return false;
  if (s.mode === 'heroSelect' || s.mode === 'bonusSelect' || s.mode === 'start') return false;
  if (s.mode === 'gameover' || s.mode === 'finished') return false;
  if (!s.currentRoom) return false;   // 还没进第一间房
  return true;
}
```

这段注释**就是你问题的答案本身**。项目的架构已经是「**内核（主程序.js）+ 可插拔宿主（经典2D.js）**」，而且内核里 21 处调用宿主的地方**全部带兜底**（下一节有审计表）。所以文字界面和 2D 之间那条缝**本来就在那里**，我们只是决定"什么时候把宿主递进去"。

**不需要把 `战斗2D.js` 拆成两半**，也不需要动任何游戏逻辑。切分表如下：

| 阶段 | 玩家在做什么 | 谁渲染 | `state.mode` | 需要的文件 | 体积 |
|---|---|---|---|---|---|
| ① 开始界面 | 看星空、点"开始游戏" | 主程序.js（DOM） | `start` | 样式 + 音频 + 主程序 | **417 KB** |
| ② 选英雄 | 挑角色 | 主程序.js（DOM） | `heroSelect` | 同上 | 同上 |
| ③ 选开局增益 | 三选一 | 主程序.js（DOM） | `bonusSelect` | 同上 | 同上 |
| ④ **实时战斗** | 进房间了，画布接管 | **经典2D.js** | 其它 + 有 `currentRoom` | **再加 4 个 2D 文件** | **+1467 KB** |

①②③ 合计 **417 KB**，④ 才需要那 **1467 KB**。这就是"开始时只加载文字界面，进 2D 再加载 2D"的确切含义 —— 而且它是代码层面可判定的，不靠猜。

**三个必须知道的技术点：**

**1. 4 个 2D 文件必须串行加载，不能并行。**
`战斗2D.js` 顶层写着 `class BattleScene extends Phaser.Scene` —— 这是**脚本解析时**就求值的。`phaser.min.js` 没先执行完，`战斗2D.js` 会直接抛 `ReferenceError`。顺序必须是：

```
phaser.min.js → 角色形象.js → 战斗2D.js → 经典2D.js
```

**2. 内核的 21 处引擎调用全部有兜底（我逐行审计过）。**

| 主程序.js 行 | 调用 | 引擎缺失时 |
|---|---|---|
| 297 | `window.试炼2D && typeof ...` | 短路跳过 |
| 432 | `if (!t2d \|\| !t2d.enterLayoutEdit)` | 提示"2D 模块未加载" |
| 2454 | `if (window.经典2D && window.经典2D.cheat)` | 提示"实时战斗尚未启动" |
| 2516 | `if (window.经典2D && typeof ...)` | try/catch 吞掉 |
| 6559 | `(window.经典2D && ...) ? ... : []` | 返回占位文案 |
| **8547** | `if (window.经典2D && window.经典2D.render()) return;` | **直接走文字渲染** |
| **9365** | `if (window.经典2D && window.经典2D.handleAction(a)) return;` | 交给内核处理 |
| 11644–11711 | `const c = window.经典2D && window.经典2D.cheat` | 提示"当前是回合制界面" |
| 11704 | `if (!h \|\| typeof h.checkEnding !== 'function')` | 提示"宿主未加载" |

**没有一处会在引擎缺失时崩溃。**

**3. `render()` 自带"引擎不可用回退"分支**（`经典2D.js` 行 1951–1959），注释原文：

> 回退：宿主可能已经把 state.mode 改成自己的标记…这里还它一个内核认识的状态

也就是说引擎没就绪时，界面会**自动退回文字模式**，而不是黑屏。

**C2 具体做法** —— 把 4 个 `<script>` 从第 732–736 行摘掉，换成 `</body>` 前的一段加载器：

```html
<script>
// 2D 引擎按需加载器：串行（战斗2D.js 顶层 extends Phaser.Scene，必须等 Phaser 就绪）
(function () {
  var FILES = [
    'vendor/phaser.min.js?v=20250907p',
    '角色形象.js?v=20250910r2',
    '战斗2D.js?v=202610210',
    '经典2D.js?v=202610220'
  ];
  var p = null;
  window.__加载2D引擎 = function () {
    if (p) return p;
    p = FILES.reduce(function (chain, src) {
      return chain.then(function () {
        return new Promise(function (ok, fail) {
          var s = document.createElement('script');
          s.src = src;
          s.onload = ok;
          s.onerror = function () { fail(new Error('加载失败: ' + src)); };
          document.head.appendChild(s);
        });
      });
    }, Promise.resolve());
    return p;
  };
})();
</script>
```

**加载时机：三个选项，我推荐第 2 个。**

| 方案 | 首屏 | 进 2D 时 | 手机流量 | 评价 |
|---|---|---|---|---|
| ① 严格按需（`shouldTakeOver` 变 true 才下） | 417 KB | **要现等 1.47 MB**（Netlify 下约 50 秒） | 最省 | 进 2D 会卡住，不推荐 |
| ② **选英雄时后台预载**（推荐） | 417 KB | 通常已就绪 | 几乎总是会用上 | 玩家挑英雄 + 选增益的时间足够下完 |
| ③ 首屏渲染后立即预载 | 417 KB（不阻塞） | 已就绪 | 可能白下 | 最稳，但对"只想看看"的人浪费流量 |

方案 ② 的挂载点：在进入 `state.mode === 'heroSelect'` 时调一次 `window.__加载2D引擎()`（不 await，后台跑）。然后在**真正需要 2D 的那一处**加一个兜底等待：

```js
// 仅此一处逻辑改动：等引擎就绪；已就绪则 Promise 立即 resolve，零额外等待
await window.__加载2D引擎();
```

**⚠️ 有一个必须处理的边界情况：读档续玩。**
如果玩家有存档且已在房间中，路径是「开始游戏 → 直接读档 → `currentRoom` 已存在 → `shouldTakeOver()` 立刻返回 true」，**中间没有选英雄的缓冲时间**。这条路径上必须 await，同时用现成的加载提示顶着。
