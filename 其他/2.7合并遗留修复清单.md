### ⑫ 走路时画面一抽一抽的
> 走起来画面一抽一抽的（可能是之前改过相机的原因），在不影响相机现有跟随功能的情况下修复这个问题。

- **落点**：相机在 P0 被改成"**横向纵向都跟随**"：
  ```js
  // 战斗2D.js:5755
  this.cameras.main.startFollow(this.hero, true, 0.12, 0.12);
  // 战斗2D.js:5673 applyCameraFollow()
  cam.setDeadzone(this.scale.width * 0.3, dz);
  cam.setFollowOffset(0, offY);
  ```
- **可疑原因（待实测）**：
  1. `lerpY = 0.12` + **纵向死区很短**（小屏上 `dz` 被 `bandBottomMax - bandTop` 压到下限 60），
     玩家每次跳跃/落地都会让纵向镜头"追一下再停"→ 视觉上一抽一抽；
  2. `setFollowOffset(0, offY)` 把死区整体下移，短屏上 `offY` 可能是负值，
     与 `setBounds` 的纵向余量（`5652`）互相拉扯；
  3. `roundPixels = true`（startFollow 第 2 个参数）+ lerp 会造成**整数像素跳动**；
  4. `applyCameraFollow()` 在 resize / 自定义布局时被反复调用 → `setDeadzone/setFollowOffset`
     在同一帧内改变（正常不会，需实测）。
- **约束（用户明确）**：**不许破坏现有的跟随功能**（P0 那套"人永远可见、地面不出画"的结论要保住）。

## 8. 二轮反馈：「还是抽，像网很卡，没老版丝滑」→ 已定位并修复（N8）

**用户第二轮原话**："还是会抽，还是那种像那种网很卡的感觉，但比之前好很多，可还是没老版丝滑。"

"比之前好很多" = 死区收窄（572 → 90）确实是原因之一；
"像网很卡" = **帧时间被拖长**，与画面内容无关 —— 顺着这个感觉去量，一次就抓到了（见 §6.1 N8）。

**定位过程（可复现）**：在真实页面里给 `game.scale` 挂一个 `resize` 计数器，再连续调 120 次 `render()`：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `render()` 单次耗时 | **4.196 ms** | **0.008 ms** |
| 120 次 render 触发的 resize | **130 次** | **0 次** |
| 引擎 `update()` 单次（对照） | 1.25 ms | — |

**为什么这条链条会把画面弄成"一抽一抽"**：
1. `经典2D.js` 的 `render()` 每帧被内核调用（`scheduleRender` → rAF）；
2. 它每帧走到 `showStage(true)`，而那里无条件执行 14 次 inline style 赋值 + `scale.refresh()`；
3. `scale.refresh()` 发出 Phaser 的 resize 事件 → 引擎 `onResize()` 每帧执行；
4. `onResize()` 里是 `layoutHudButtons`（HUD 全量重排）+ **`applyCameraFollow()`（每帧重设 `setDeadzone` / `setFollowOffset`）**；
5. 相机正在 lerp 跟随的途中，参数每帧被重设 → 跟随被反复打断；HUD 也每帧重排。

**老版为什么没有这个毛病**：老版宿主是 `试炼程序.js`，它的舞台显隐只在**切视图**时调一次，
不存在"每帧 refresh"。所以同一份引擎在老版丝滑、在新版抽 —— 差别在宿主，不在引擎。

**修法（两处，都在宿主 `经典2D.js`）**
- `showStage()` 加"状态没变就不动 DOM"的早退；`syncLandscape()` 仍然每帧走（自带短路，
  它是"该横屏却没横屏 → 记待补标记"的唯一检查点，不能省）。
- 画布尺寸变化改由 `onViewportChange()` 承担，同时挂 `window.resize` 与 `visualViewport.resize`
  （移动端地址栏收缩有的浏览器只发后者），里面保留原有的"尺寸变了才重排 + 记待补标记"逻辑。

**顺带处理的第二处取整抖动**：`startFollow(hero, true→false, 0.12, 0.12)`。
相机是 lerp 跟随，收敛期速度是小数（如 0.4px/帧），`roundPixels = true` 会把它取整成
`0,0,1,0,0,1` 的跳步 —— 这正是"持续行走时一抽一抽"的观感来源之一。本作不是像素画风
（纹理是程序化生成的渐变图形），关掉它几乎看不出画质差别；若真机觉得画面变糊，
把那一行的 `false` 改回 `true` 即可。

**回归**：`测试/2D引擎回归.html` **28 项全通过**（改了 `startFollow` 之后重跑）。

### 9.1 N9 · 🔴「抽动更严重」= 我上一轮把每帧 refresh 拿掉后，**画布塌成了 0×0**

上一轮为了修"每帧重活"（N8），我把 `showStage()` 改成"只在状态变化时 refresh"。
但漏了一种情况：**舞台被收起过再显示时**（死亡结算 / 结局 / 降级 / `reset()`+`start()`），
`#trial2DStage` 隐藏 → 容器尺寸变成 0 → Phaser 在 RESIZE 模式下把画布也缩成 **0×0**；
再次显示时若那一帧浏览器还没算完布局（`clientWidth` 仍为 0），`scale.refresh()` 就是**空转**，
画布于是**永久停在 0×0** —— 渲染缩放全错，画面错位/抖动/拉伸。

原代码靠"每帧无脑 refresh"兜住了它（代价就是 N8 那 4.2ms/帧）。
**实测**：`reset()` + `start()` 之后 `game.scale` = `[0, 0]`（画布确实是塌的）。

**修法（两道保险）**
- `stageWarmup`：舞台显示后的前 12 帧，逐帧比对 **canvas host** 的实际尺寸与 Phaser 的 `scale`，
  不一致才补一次 `refreshStageScale()`；稳定期零开销。
  （比的是 host 而不是 stage —— stage 里还有标题条，高度天然比画布大，拿它比会每帧都"不匹配"。）
- `ResizeObserver` 观察 canvas host：容器尺寸**真的变了**就补 refresh。
  observe 的是 host 不是 canvas —— canvas 尺寸由 Phaser 自己写，观察它会自激。

**实测**：修复后 `scale` 与 host 一致（`1908×1014`），`render()` 仍是 **0.002 ms**，
启动阶段只触发 2 次 resize（不是每帧）。

> 顺带把 `roundPixels` **改回 true**：上一轮我把它设成 false 想消除"lerp 小数速度被取整"的跳步，
> 实机反馈是**更抽了** —— 相机落在半像素上后，程序化生成的纹理每帧在不同采样位置重采样，
> 那是整幅画面在**闪烁/蠕动**，比取整跳步难看得多。取整跳步最多让移动"一格格"，
> 半像素采样是**全屏都在抖**。

### 11.1 N16 · 🔴 2.7 换了 body 标记，但那套 2D 专用 CSS 没跟上

`经典2D.js` 给 `body` 打的标记是 **`classic2d`**（`MODE_TAG`），
而"2D 期间该收起来的东西"这套 CSS 全部挂在 **`body.realtime-trial`**（试炼时代的标记）上。
合并时换了标记、漏了同步 CSS，一下子暴露三个问题（用户报了其中两个）：

| 后果 | 说明 |
|---|---|
| **2D 画面里页面还能滚动** | `body.realtime-trial { overflow: hidden }` 不生效 |
| **背景三层特效在整场战斗里持续跑** | `.nebula-layer` / `.stars-layer` / `.particle-container` 没被 `display:none` |
| 侧边栏那套规则没跟上 | `☰` 已另行补过（见 11.4） |

第 ② 条**不是观感问题而是性能问题**：`.nebula` 是 60vw 的 div 配 **`filter: blur(80px)`**、
外加 30 秒无限漂移动画；`.particle-container` 里的粒子更是由 JS 逐个创建/移动的 DOM。
两者叠在一场实时战斗底下，等于每帧都在白烧主线程与 GPU —— **手机上是实打实的掉帧来源**。

**修法**：把三组选择器都扩展成同时匹配 `body.classic2d`；
另外在 `showStage()` 里对 `document.documentElement` 也锁 `overflow`/`overscroll-behavior`
（`body{overflow:hidden}` 挡不住"内容比视口高时由根元素接管滚动条"）。

**实测**：`bodyOverflow: hidden`、`htmlOverflow: hidden`、`canScroll: false`、
`nebula/particles: display none`。

### 11.2 N17 · 🔴 标题处"隐约看见文字界面"

`.trial2d-stage` 原本是**嵌在文字界面里的一个小舞台**的样式：`1px 边框` + `14px 圆角` +

边框与圆角于是把下面的 DOM 文字界面从四周和四个角**透出来**（用户描述的"在标题处隐约
看见文字界面的画面"），下边距还会把底部顶起 10px。

`background`，并把它们加进 `STAGE_INLINE`（退出时一并还原）。

**实测**：`stageBorder: 0px`、`stageRadius: 0px`、`stageMargin: 0px`。

### 11.3 N18 · 🔴 难度切换的两个真问题

## 12. 五轮反馈：「2D 存档要从第一层重打」+「自定义难度界面关不掉」

### 12.1 N20 · 🔴 读档必回第一层（存档形同虚设）

**用户原话**："2D画面的存档功能有问题，重进后得从第一层重新打。"

**两个写死值叠加**：

| 位置 | 代码 | 后果 |
|---|---|---|
| 引擎 `beginRun()` | `this.floor = 1;` + `this.makeFloorMap(1)` | 每次开局都从第 1 层重新建图 |
| 宿主 `startRun()` | `s.roomIndex = 0; s.currentRoom = rooms[0]` | 内核镜像也被强行归零 |

于是"存档在第 3 层第 3 间"→ 重进后回到第 1 层第 1 间。

**修法**：起始位置改由宿主在 `startRun` 的 payload 里下发，**引擎开局直接落在存档位置上**
（不走 `gotoRoom` —— 那条路依赖场景已就绪，时序不可靠；而 `beginRun` 本来就是建图的时机）：

```js
// 引擎 beginRun
var startFloor = Math.max(1, Math.round(d.floor || 1));
var startIdx   = Math.max(0, Math.round(d.roomIndex || 0));
this.floor = startFloor;
this._floorRoomsCleared = d.roomsClearedThisFloor != null ? d.roomsClearedThisFloor : startIdx;
this.floorMap = this.makeFloorMap(startFloor);
if (startIdx > 0 && this.floorMap.nodes[startIdx]) this.floorMap.current = this.floorMap.nodes[startIdx];
this.roomNode = this.floorMap.current;  this.roomNode.visited = true;
```

**实测**（真实存档 → 刷新 → 读档）：

| | 存档 | 读档后引擎 |
|---|---|---|
| 层数 | 3 | **3** ✅ |
| 房间 | 第 3 间（col 2 · 商店房） | **col 2 · shop** ✅ |
| 生命 | 20 | **20** ✅ |
| 金币 | 77 | **77** ✅ |

### 12.2 N21 · 🔴 换层存档的时序反了（存的是"新层数 + 旧层房间"）

`nextFloor()` 里 `notifyCheckpoint('floor')` 排在 `rt:floor` **之前**，而宿主的 `onFloor`
正是在这个事件里**生成新层的房间序列 / 重掷环境 / 下发新规划**的。

于是换层那一刻写盘的组合是：`floor = 新层` + `rooms / environment = 旧层` —— 自相矛盾，
读档后地图与房间类型会整个错位。

**修法**：把 `notifyCheckpoint('floor')` 移到 `rt:floor` **之后**（此时 state 与引擎都已是新层的一致状态）。

顺带在宿主 `onCheckpoint` 里补一层防御：**房间位置以引擎快照的 `snap.room.col` 为准**
（进房时的 `rt:room` 已经同步过一次，这里再对一次，万一事件没绑上顺序有变也不会存错位置）。

### 12.3 N22 · 🟡 自定义难度面板关不掉（"收起"只折叠主体）

**用户原话**："自定义难度界面出来后无法关闭，把'收起'按钮改为关闭。"

原实现里那颗按钮是**折叠/展开面板主体**（`body.collapsed` + 文案在"收起/展开"之间切换），
**面板外壳永远留着**。文字界面还凑合，但 2D 里这个面板是浮层
（`position: fixed` + `z-index: 9500`，见 §11.3）——于是它**挡住整个战场而且关不掉**。

**修法**（按你的要求）
- 按钮文案 `收起` → **`关闭`**，行为改成真正的关闭：`panel.classList.add('hidden')`
  （同时清掉折叠态，下次打开是展开的）；
- 面板标题栏不再整条可点（浮层下"点标题就折叠"极易误触）；
- **补一条"叫回来"的路**：值已经是「自定义」时再点一次难度下拉也要能打开面板
  —— `change` 在值没变时不触发，所以给两个下拉补了 `click` 兜底，否则关掉就再也打不开。

**实测**：切自定义 → `display: block`（浮在画布上）；点「关闭」→ `display: none`；
再点下拉 → 面板回来 ✅

## 13. 六轮反馈（4 条）：难度特效 / 缩放文字 / 越界检查 / 图鉴分类

### 13.1 N23 · 🟡 局内切难度，场景特效不变

**用户原话**："进 2D 前调为地狱难度进入后会有特效，但在局内切换难度特效的状态不会变。"

场景主题（星雾浓度 / **上升火星** / 雾色）由 `applyEnvironment(diff)` 负责，而它**只在 `beginRun` 里调用过一次** ——
`applyEnvironment` 也没有对外的 API，宿主在难度变更时想调都调不到。

**修法**：引擎新增 API `setDifficultyTheme(diff)`；宿主在难度签名变化时一并调用
（与 `pushEnemyScaler / pushPulseProfile / pushCursesEnv` 同一处）。
现在局内切到地狱会立刻出现上升火星，切回简单/普通火星会消散。

### 13.2 N24 · 🟡 自定义按键缩放后文字发虚

**用户原话**："自定义按键缩放：放大和缩小文字都会不清晰，让文字不管在多大的大小下都清晰。"

**原因**：Phaser 的 Text 是**预渲染纹理** —— 布局编辑器里的 `setScale(s)` 只是把那张固定分辨率的图
拉大/压小，放到 250% 自然糊。

**修法**：新增 `sharpenScaledText(obj, scale)`，在**缩放变化时**同步提高 `Text.resolution`
（量化到 0.25 一档，避免同尺寸反复重建纹理）：

| 情形 | 处理 |
|---|---|
| 放大（s>1） | `resolution = s × devicePixelRatio`（上限 4）→ 按目标尺寸重新栅格化，边缘回锐 |
| 缩小（s<1） | 保持 `resolution ≥ 1`（纹理缩小本身清晰） |
| 不变 | 直接 return，零开销 |

`setResolution` 不改变显示尺寸（Phaser 会同步纹理与 size），所以依赖坐标的布局代码不受影响。

> 诚实的边界：**非整数缩放的线性过滤**是渲染层的固有限制，那部分靠分辨率解决不了。
> 但"放大后明显发虚"这一类已经修掉。

### 13.3 N25 · 越界文字检查（结论：UI 层没有越界）

写了一个自动检测：遍历场景里所有可见 Text，用 `getBounds()` 取世界包围盒，与画布边界比对；

| HUD 按 774×334 重排 | 剩余告警全是**误报**，已逐条确认 |

误报的两类来源（记下来免得下次重踩）：
1. **敌人头顶的名字/攻值标签**是**世界空间**对象（跟着敌人走），本来就会跑到画外 —— 不是 UI；

## 14. 七轮反馈：「房间分支没了，加回来」

**用户原话**："现在怎么没有房间的分支了，都是一条线，我感觉之前那种有分支挺好的，把分支加回来。"

### 14.1 N27 · 地图退化成一条直线的原因

合并时宿主为了让「经典第 i 间 = 2D 第 i 间」严格对应，把**每间房单独放一列**：

```js
cols: rooms.map(r => [{ type: r.type }])   // 每列 1 个 → 直线
```

引擎的 `linkCols()` 只在"相邻两列之间存在多个节点"时才画得出分叉，
每列 1 个自然就是一条直线 —— 玩家体感是"一关一关往下走"，选路感全没了。

### 14.2 修法（两处，缺一不可）

**① 宿主：中间列各放 2 个候选**（`planFromRooms`）

| 列 | 候选数 | 理由 |
|---|---|---|
| 起点列 | 1 | 玩家开局就在这里，多给一个等于放一扇**永远进不去**的门 |
| 中间列 | **2** | 玩家每次开门都能在"主线房"和"支线房"之间挑一个 |
| Boss 列 | 1 | 分叉会变成两个层主 |

支线类型从内核同一套房间池抽（`enemy` 权重更高），并沿用内核首层不出现商店/休整的规则。

**② 引擎：`linkCols` 从"随机挑一个"改成"连到全部"**

这一条是**顺带挖出来的**：原来每个节点只随机连下一列的**一个**节点：

```js
n.links.push(cands[ri(0, cands.length - 1)].id);   // 只连 1 个
```

于是"在某一列能走哪几条路"完全由连线决定、**玩家没得选** ——
配上每列 1~2 个候选，就会出现"开局只有一条出路"的情况，分支形同虚设。
改成 `cands.forEach(m => n.links.push(m.id))` 之后，相邻两列之间才是**真正的分叉**。

### 14.3 支线要写回内核（否则存档会说谎）

玩家走的可能是支线，而内核的 `state.rooms[col]` 记的是主线房型。
`onRoom` 现在会把**实际房型写回** `s.rooms[col]` —— 于是存档 / 读档 / 结算
看到的都是"真正打过的那一间"。

## 15. 八轮反馈：「祭坛按钮文字越界」

**用户原话**："祭坛房间内'献祭4生命解除一条诅咒'几个字越界了，做完后改。"

### 15.1 N28 · 面板按钮文字冲出底板（三层修法）

**根因**：`paintButton` 里只有 `shape === 'pill'` 的按钮会在文字变长时**自动加宽**：

```js
var need = Math.round(b.text.width + padX * 2 + icoW + gap);
if (b.w < need && b.shape === 'pill') b.w = need;     // ← 只有 pill
```

而画内面板里的按钮（`uiButton` → `shape: 'card'`）宽度是布局算好的、不能自由伸缩。
再叠上 `buildChoiceLayer` 里**写死的宽度上限**（`mini ? 130 : 156`，与文案长度无关），
"献祭 4 生命 · 解除一条诅咒"这类长按钮就必然冲出底板。

**修法（三层，任一层单独都不够）**

| 层 | 做法 |
|---|---|

## 16. 九轮修正：「不要把每个房间都连上」

**用户原话**："分支是有了，但不要把每个房间都连上啊，要让玩家有选择这样才好玩，
比如你选完敌袭房间下一个就只能进精英房间，不能选择进另一个宝箱房间。"

### 16.1 我上一轮把"分支"做错了方向

§14 里我把 `linkCols` 从"每节点随机连 1 个"改成了**连到下一列的全部**，理由是
"起点只有一条出路、玩家没得选"。这个诊断只对了一半：

- **对**：起点（每列只有 1 个节点时）确实需要 2 条出路，否则一开局就没选择；
- **错**：把**所有**节点都改成全连。全连看起来"到处都是分叉"，实际是
  **每条路都通向同一批房间** —— 玩家选哪间都一样，反而彻底消灭了取舍
  （这正是用户说的"不要把每个房间都连上"）。

### 16.2 正确的规则：有约束的连线

| 规则 | 说明 |
|---|---|
| 每个节点默认 **1 条**出边 | "进了这间，下一间就定了"——就是用户举的例子（选了敌袭 → 只能进精英） |
| **每列恰好一个**分叉点给 **2 条** | 否则整层一个选择点都没有、又变回直线；起点列只有 1 个节点，天然是分叉点，玩家一开局就能选方向 |
| "哪个节点是分叉点"**随机** | 于是"刚才选了哪一间"会直接影响"这一列还有没有得选"——**选择因此有了后果** |
| 每个房间**至少一个入口** | 兜底：否则地图上会出现永远进不去的门 |
| 每个非 Boss 节点**至少一条出边** | 兜底：否则玩家会卡在死路里 |

### 16.3 实测（6 间房的层 · 连跑 8 次随机地图）

```
起点 0.0:敌袭 → 2 条        ← 开局能选方向
     1.0:精英 → 1 条        ← 进了精英，下一间就定了
     1.1:祭坛 → 2 条        ← 进了祭坛，下一列还有得选
     2.0:商店 → 2 条
     2.1:敌袭 → 1 条
     3.0:休整 → 2 条
     3.1:镜像 → 1 条
     4.x     → 1 条（下一列只有 Boss）
     5.0:Boss → 终点
```

| 检查 | 8 次结果 |
|---|---|
| 进不去的房间 | **0** |
| 走不出去的死路 | **0** |
| 开局可选方向数 | **2 / 2 / 2 / 2 / 2 / 2 / 2 / 2** |
| 每层分叉点数 | **4 / 4 / 4 / 4 / 4 / 4 / 4 / 4** |
| 出边数分布（示例） | `2,1,2,1,2,2,1,1,1,0` —— 大量节点只有 1 条，**不是全连** |

## 17. 十轮反馈：「2D 的存档功能有问题」+「还有存档管理的相关功能」

用户没给具体现象，所以**系统地把"存档 → 刷新 → 读档"的每一项都对了一遍**，
另外把**存档管理**（切槽位 / 重置 / 导入）这条路径也走了一遍。查出 3 个真问题。

### 17.1 N30 · 🔴 读档后房间**差一间**

**现象**：存档在第 2 层第 3 间（col=2, shop），读档后引擎落在 **col=1**。

**根因**：`beginRun` 用**数组下标**取起始房间：

```js
this.floorMap.current = this.floorMap.nodes[startIdx];
```

而 `nodes` 是按"列 → 行"铺平的数组，经典模式的规划**每列有 2 个候选**（§14），于是：

| 下标 | 实际是谁 |
|---|---|
| 0 | col0 |
| 1 | col1 的第一个 |
| **2** | **col1 的第二个** ← 不是 col2！ |
| 3 | col2 的第一个 |

→ 读档位置**整体偏前**。

**修法**：按 **`col`（列号）** 找，而不是下标；同一列取第一个（主线房，与存档里 `rooms[col]` 的类型一致）。

### 17.2 N31 · 🔴 诅咒完全不随存档恢复

宿主 `startRun` 的 payload 里写死了 `curses: []`：

```js
curses: [],          // ← 存档里的诅咒全部失效
```

于是读档续玩时引擎的 `curses` 是空的 —— **腐化脉冲不会结算任何诅咒**，
玩家身上那几条诅咒等于凭空消失了。改成 `curses: rtCurses(s)`。

### 17.3 N32 · 🔴 存档管理：切槽位 / 重置 / 导入之后，**2D 引擎还在跑旧局**

引擎是**全局单例**、自己跑着自己那一局。内核这几处只改了 `state`：

| 入口 | 原来的样子 | 后果 |
|---|---|---|
| 存档管理「加载」(`case 'load'`) | `setActiveSlot` → `loadGame()` → `render()` | 数值变了，但**画布上还是旧战场**、怪物还是原来那批 —— 玩家以为"切档没生效" |
| `resetCurrentSlot()`（重新开始） | 重置 state → `render()` | 画布还盖在最上面，**下面的英雄按钮点不到** |
| 导入存档 (`legacyFileInput` 的 change) | `Object.assign(state, data)` → `render()` | 同上 |

**内核从头到尾没有调用过 `window.经典2D.reset()`**（grep 实测 0 处）。

**修法**：新增统一入口

```js
function notifyHostRunReset() {
  if (window.经典2D && typeof window.经典2D.reset === 'function') window.经典2D.reset();
}
```

并在这三个入口调用。`经典2D.reset()` 会 `stop()` 引擎；随后的 `render()` 因为 `running === false`
会重新 `startRun()`，而 `startRun` 读的就是**新的 state**。
