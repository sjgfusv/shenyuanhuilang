## 0. 先说结论

**两条，对应两个议题。**

1. **数值是真的没改，而且不是"漏了一行"，是整片没接上。**  
   20 个随机事件里只有 **2 个**（幸运骰子、商队护送）是按设计工作的；  
   12 个部分生效（属性/药水延迟、代价被免），**6 个完全无效或净亏**  
   —— 包括「暗影交易」（−20 生命换 5 件遗物，结果什么都没发生）和  
   「神秘商人」（−30 金币，遗物一件不到，**唯一一个纯亏**的事件）。  
   根因是 2D 里内核与引擎是两份数据，只有三条下发通道，而**战斗奖励和随机事件都不在通道的调用清单里**。  
   再往上还有一层：经验在 2D 里是**死资源**（引擎从不读），力量药水**根本没实现**，  
   两套遗物并存：效果是 2.9 为 2D 重写的（更好），但**映射表没跟着换** ——  
   事件里写"战斗怒火"、HUD 上显示"重击"，同一件东西两个名字（§1.5）。
2. **垂直房间 = 把横向房间转 90°**：宽度锁一屏、长度搬到 y 轴、相机纵向滚、左右两面墙、  
   每 220px 一层**完整楼板**。**不是"多堆几个浮台"，是换坐标系。**  
   走法：**`S` 防御、`↓` 穿一层** —— 把 `S` / `↓` 现在共用的"防御"拆开（`:4101-4102`），  
   不用特地跳一下，站着按 ↓ 就下一层。**而且一次只能下一层**：  
   否则按住 ↓ 一路穿到底，10 层楼板等于白做，玩家直接掉到底开门走人（§2.5）。  
   好消息：重力不用改、单向平台不用改（能下也能上，跳高 389 > 层距 220）、  
   井底仍用原来的 `groundY`（掉坑判定和传送门都不用动）。  
   坏消息：**相机、边界、敌人分布、魂晶分布、掉落回传、目标物投放全要改** ——  
   500~600 行 + 18 处（§2.9）。这是 3.0 真正的工作量。  
   配套：**敌人也会穿层追下来**（§2.6），加上**五个机关陷阱**（§2.7~2.8，只在竖塔做）。  
   陷阱的核心是"出其不意"—— 竖塔视野受限、有纵向弹道、穿层时不能举盾且落点未知，这三样横向房间都没有。  
   最需要作者拍板的是**漏怪怎么办**（§2.10 ①）：10 层塔漏一只，爬回去很烦。

## 1. 议题一：文字 → 2D 迁移遗留总账

> 作者的原话是"很多问题都是当时从文字界面转 2D 时没考虑周全，面向结果编程了"。  
> 查完之后**这个判断完全成立**，而且比预想的严重：20 个随机事件里，只有 2 个是按设计工作的。

### 1.1 一句话结论：现在只有金币是真的

| 产出类型                                 | 在 2D 里的实际结果 | 原因                                                                 |
| ------------------------------------ | ----------- | ------------------------------------------------------------------ |
| **金币**                               | ✅ 有效        | 内核是权威，`advanceToNextRoom` / `settleRoomGold` 会 `syncPoints()` 推给引擎 |
| **经验**                               | ❌ 死资源       | 引擎从不读 xp，2D 也没有升级 / 经验支付                                           |
| **生命 / 生命上限**                        | ❌ 全丢        | 清房时 `syncHp()` 用**引擎值覆盖内核值**，事件改的血被抹掉                              |
| **攻击 / 暴击 / 闪避 / 吸血 / 荆棘 / 连击 / 斩杀** | ⚠️ 延迟       | 内核改了但没 `pushStats()`，要等下一次商店/休整/祭坛/遗物才一次性补上                        |
| **护盾**                               | ⚠️ 反向       | 引擎扣了内核不知道，任何 `pushStats` 都会把盾补回来                                   |
| **治疗药水**                             | ⚠️ 延迟       | 同上                                                                 |
| **力量药水**                             | ❌ 2D 引擎不存在  | 连文字模式里唯一的使用入口（Boss 前界面）在 2D 里也不出现                                  |
| **遗物**                               | ❌ 不下发       | 事件走内核 `chooseRelicByRarity()`，绕过了宿主的 `addRelic()`                  |

### 1.2 为什么会这样：两份数据 + 三条通道

2D 模式下，内核（`主程序.js` 的 `state.player`）和引擎（`战斗2D.js` 的 `this.hero`）是**两份数据**。  
中间只有三条通道：

| 通道             | 位置             | 方向          | 谁在调                          |
| -------------- | -------------- | ----------- | ---------------------------- |
| `pushStats()`  | `经典2D.js:2176` | 内核 → 引擎     | 9 处（见下）                      |
| `pushRelics()` | `经典2D.js:820`  | 内核 → 引擎     | 2 处（`addRelic` / `startRun`） |
| `syncHp()`     | `经典2D.js:1801` | **引擎 → 内核** | 3 处（清房 / 存档点 / 结束）           |

`pushStats()` 的全部调用点（实测 grep）：

```
经典2D.js:881   addRelic()         ← 拿到遗物
经典2D.js:906   relicFallback()    ← 遗物池抽干的兜底
经典2D.js:1256  shopBuy            ← 画内商店
经典2D.js:1959  buyShopItem()      ← 商店面板
经典2D.js:2019  restAction()       ← 休整点
经典2D.js:2069  shrineAction()     ← 祭坛房
经典2D.js:2428~2452  cheat.*       ← 作弊面板
```

**「战斗奖励」和「随机事件」都不在这份清单里** —— 这就是一切问题的根。  
迁移的时候是"先把界面接上、能看到数字"（面向结果），至于"这个数字有没有真的到引擎里"，没有验过。

### 1.4 B 类：文字时代的概念在 2D 里不存在（6 条）

这一类比 A 类麻烦：不是"漏了一行"，是**这个机制在实时战斗里没有对应物**。

| #  | 字段 / 机制                         | 文字模式语义                                                 | 2D 里的现状                                                               | 修法方向                                                |
| -- | ------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------- | --------------------------------------------------- |
| B1 | **经验 `xp`**                     | 第二货币：金币不够可花经验买东西（`主程序.js:7837/7855`）；知识祭坛 −20、战斗导师 −15 | 引擎 `grep "\.xp"` = **0**。每场照给（`经典2D.js:1788`），但**没有任何用途**             | 补「金币不够可花经验」的支付分支 —— 最省，且两个事件立刻有了真实代价                |
| B2 | **力量药水**                        | 下一场战斗攻击大幅提升（`pendingAttackBoost = 3`，`主程序.js:6188`）    | `grep strength` 两个 2D 文件 = **0**。`usePotion()` `战斗2D.js:12476` 只认治疗药水 | **补实现**，方案见 §1.8                                    |
| B3 | **`pendingAttackBoost`**        | 下一次攻击 +N 伤害                                            | 2D 不读                                                                 | 跟着 B2 一起做，或废弃                                       |
| B4 | **`hasLifeShield`**（开局增益「生命护盾」） | 每回合获得 2 点护盾                                            | 2D 没有"回合"，也没实现                                                        | 改成「每房间开始 +2 护盾」（房间级，等价语义）                           |
| B5 | **`hasDoubleGold`**（「双倍金币」）     | 战斗金币 +50%                                              | `settleRoomGold` 只用难度倍率 `goldMultiplier()`，**不读它**                    | 加一句 `if (s.hasDoubleGold) gain = round(gain * 1.5)` |
| B6 | **`hasExpBoost`**（「经验加成」）       | 经验 +50%                                                | 只在 xp 计算里用，而 xp 无用 → **等效无效**                                         | B1 修完自动活                                            |

> B4 / B5 是**开局增益池 30 项里唯一两个彻底无效的**，其余属性类之所以有效，  
> 是因为 `startRun` 会 `playerStats(s)` 把整份数据推一遍（`经典2D.js:1027`）。  
> 也就是说：**开局增益能生效是"碰巧"，不是设计** —— 它只是恰好赶上了开局那次全量下发。

### 1.5 C 类：遗物映射表 —— P3 留下的半成品

> 其实那些效果是 2.9 **故意为 2D 重写**的，比文字模式的"攻击 +1"好得多。  
> 真正的问题不是效果，是**名字**。

**先把设计意图摆出来**（`战斗2D.js:276` 的注释原文）：

#### 修法：三个方案，效果都不变

**关键前提：改发 `RELIC_POOL` 不会改变任何效果。**  
因为老遗物最终也是走 `RELIC_FX` 那 27 个 id 里的某一个 —— 现在绕了一圈才到，改完是直达。  
变的只有**名字、概率分布、事件池大小**这三样。

| 方案                    | 做法                           | 效果变化  | 名字   | 代价                                                  |
| --------------------- | ---------------------------- | ----- | ---- | --------------------------------------------------- |
| **A · 不动**            | 补完 `pushRelics()` 就收工        | 无     | 继续泄漏 | 玩家永远看不懂"战斗怒火"和"重击"的关系                               |

### 1.8 力量药水：2D 补实现方案

**现状**：文字模式里 `pendingAttackBoost = 3`（`主程序.js:6188`）——"下一次攻击 +3 伤害"，  
使用入口是 Boss 前那个专属界面（`主程序.js:9216`）。**2D 接管后这个界面不出现**，  
所以力量药水在 2D 里既没有实现、也没有入口，但商店照卖 18 金币、奖励池和许愿池照发。

**为什么不能照搬"+3 一次"**：2D 一次挥砍是 5~~15 伤害、一场战斗 15~~20 刀，  
"下一次 +3" 等于一次性 +3 总伤害 —— 在实时战斗里等于没有。语义必须重译。

**建议方案：进房自动生效，本房间攻击 ×1.25**

| 项   | 做法                                        | 理由                        |
| --- | ----------------------------------------- | ------------------------- |
| 语义  | 「下一场战斗」→「下一间战斗房」                          | 最贴近原文，且 2D 的"一场战斗"就是"一间房" |
| 触发  | **进入战斗房时自动消耗 1 瓶**，不需要新按键                 | 触摸端底部已经排了 8 个按钮，加一个会挤爆    |
| 效果  | 本房间内 `rollPlayerDamage` 的 `base` × 1.25   | 复用现有伤害出口，不新增计算路径          |
| 提示  | 进房飘字「力量药水 · 攻击 ×1.25」，HUD 的「攻」后面挂 `×1.25` | 不提示的话玩家不知道喝了              |
| 不消耗 | 非战斗房（商店/休整/事件/宝箱/祭坛）不触发                   | 否则进商店就白喝一瓶                |

**数值校准**：

| 对比项       | 价格   | 效果           | 一场战斗（约 18 刀，攻击 10）总量 |
| --------- | ---- | ------------ | -------------------- |
| 锐利之刃      | 20 金 | **永久** +2 攻击 | +36，且跨房间累积           |
| 力量药水（现方案） | 18 金 | 一场 ×1.25     | +45，一次性              |

按 1.25 算，单场收益略高于锐利之刃但**不跨房间**，价格 18 是合理的；  
若取 1.3，建议价格提到 22。

**代码落点（5 处，都不大）**：

| # | 改什么                                                                                 | 位置                                          |
| - | ----------------------------------------------------------------------------------- | ------------------------------------------- |
| 1 | `playerStats()` 增加 `strength: p.strengthPotions \|\| 0`                             | `经典2D.js:427`                               |
| 2 | `applyPlayerStats` 增加 `if (p.strength !== undefined) h.strength = p.strength;`      | `战斗2D.js:5691`                              |
| 3 | 进房时（仅战斗房）`hero.strength--`，置 `this._roomStrength = 1.25`，飘字                         | `战斗2D.js` `buildLevel` 的 `startMechanic` 之前 |
| 4 | `rollPlayerDamage` 里 `base *= (this._roomStrength \|\| 1)`                          | `战斗2D.js:11193`                             |
| 5 | **回写内核**：引擎消耗后调 `bridge.consume('strength', 1)` → 宿主 `strengthPotions--` + `pushStats()` | `经典2D.js` 的 `makeBridge()`                  |

> **第 5 条是关键，也是 A4（护盾）的同一类问题**：  
> 凡是"引擎侧会消耗、内核不知道"的资源（护盾、力量药水），都会被下一次 `pushStats` 补回来。  
> 建议 3.0 顺手建一个通用回写通道 `bridge.consume(key, n)`，把护盾和力量药水一起解决，  
> 而不是各打各的补丁。

### 1.9 拿了之后要看得见

> **作者澄清**：这一条和"数值有没有生效"是两件事。
> 原话是「我当时说的体感不明显是指选奖励、选事件等没有以前文字界面那么直观，
> 因为之前有飘字特效，而 2D 选完之后就啥也没了，不能直观地看到我"拿了"」。
> **排除当前奖励未结算的问题**（那是 §1.3 的 A 类 bug）—— 这里只谈"生效了，但玩家没看见"。

#### 现状：2D 接管后，反馈链断了

文字界面时代，`spawnDamageFloat()` 会在页面上飘一个 `+1`。
2D 接管后，那套 DOM 飘字**要么被 `body.classic2d` 收起、要么被画布盖住** —— 总之玩家什么都看不到。

| 入口 | 选完之后发生什么 | 玩家看到什么 |
|---|---|---|
| 战斗奖励 | 面板关闭 → 直接进下一间房 | **没有** |
| 随机事件 | 面板关闭 → 直接进下一间房 | **没有** |
| 商店购买 | 面板重开刷新 | 只有金币数字变了 |
| 休整 / 祭坛 | 面板关闭 → 进下一间房 | **没有** |

**所以问题不是"数值没变"，是"变了但没有一个时刻告诉玩家"** —— 而这两件事在玩家体感上是一样的。

#### 设计：三层反馈，都不用飘字

作者说"不是让你搬飘字特效，而是设计一种直观的方式"。所以不用 `+1` 这种飞出去的数字，改成三层：

**第一层 · 选前预告（卡片上写清楚会变成多少）**

| 现在 | 改成 |
|---|---|
| `攻击 +1` | `攻击 5 → 6` |
| `生命上限 +4` | `生命 24 → 28` |
| `护盾 +3` | `护盾 0 → 3` |
| `金币 +12` | `金币 34 → 46` |

这一层解决"我不知道这个选项到底给我什么"。实现只要在 `openRewardPanel` 生成卡片时读一次当前值。

**第二层 · 选后确认（变化横幅）**

选完之后，画布上方出现一条 1.2 秒的横幅，逐行列出"变了什么"：

```
┌─────────────────────────┐
│  攻击  5 → 6            │
│  护盾  0 → 3            │
└─────────────────────────┘
```

| 规格 | 值 | 理由 |
|---|---|---|
| 位置 | 屏幕上方 1/4（HUD 下沿再往下 40px） | 不挡战斗区，也不被 HUD 盖住 |
| 时长 | 1.2s（0.15s 淡入 / 0.9s 停留 / 0.15s 淡出） | 够读完，不打断节奏 |
| 样式 | 复用 `showCenter` 的面板语言（`:15400` 附近） | 与引擎既有横幅同源，不发明新样式 |
| 颜色 | 每项用属性语义色（沿用 `statDefs` `:3777`） | 攻击红 / 暴击黄 / 闪避蓝 …… 和 HUD 一一对应 |
| 行数 | 最多 4 行，超出合并成"等 N 项" | 防止事件一次改 6 项时糊一屏 |
| 无变化 | **不显示** | 避免"什么都没发生"还弹横幅 |

**第三层 · HUD 微动（看得见的那一位动一下）**

| 做法 | 说明 |
|---|---|
| 对应属性位放大 1.25 倍再回弹（0.35s） | 让"攻 6"这个数字自己被注意到 |
| 数字从旧值滚动到新值（0.4s） | 比直接跳变更有"涨了"的感觉 |
| 手机横屏属性面板被收起时，**跳过这一层** | 收起了就没法动，硬展开反而打断 |

#### 关键实现：用「快照对比」而不是手写文案

**这是整个方案的核心** —— 不要给 20 个事件、13 个奖励、12 件商品各写一句反馈文案。
那一定会漏、会漂移（项目里已经有过"图鉴手抄一份结果抄错"的教训）。

改成：**apply 前后各拍一次快照，diff 出变化，自动生成横幅**。

```js
// 经典2D.js 新增
function snapshotStats(s) {
  var p = s.player || {}, d = derivedStats(s);
  return {
    attack: p.attack, maxHp: p.maxHp, hp: p.hp, shield: p.shield || 0,
    gold: p.gold || 0, potions: p.potions || 0, xp: p.xp || 0,
    critRate: d.critRate, critDamage: d.critDamage, dodge: d.dodge,
    thorn: d.thorn, vampire: d.vampire, combo: d.combo, execute: d.execute
  };
}

// 包一层：任何"会改数值"的入口都走它
function withFeedback(fn) {
  var s = S(); if (!s) return fn();
  var before = snapshotStats(s);
  var r = fn();
  var after = snapshotStats(s);
  var gain = diffStats(before, after);   // [{label:"攻击", from:5, to:6, color:"#ff8a7a"}, ...]
  if (gain.length) {
    pushStats();                          // §1.3 的 A 类修复
    try { engine().showGain(gain); } catch (e) { /* 忽略 */ }
  }
  return r;
}
```

**包在哪**（一次性覆盖全部入口）：

| 入口 | 位置 |
|---|---|
| 战斗奖励 | `onChoiceResult` reward 分支 `:1613` 的 `opt.apply()` |
| 随机事件 | event 分支 `:1686` 的 `ev.apply()` |
| 商店购买 | `buyShopItem` `:1956` 的 `it.apply()` |
| 休整点 | `restAction` `:2019` 附近 |
| 祭坛房 | `shrineAction` `:2069` 附近 |
| 深渊裂隙 | `onChoiceResult` rift 分支 |

> 一个 `withFeedback` 包住六个入口，**以后新增任何奖励/事件都自动有反馈**。
> 这比"每个选项写一句文案"省得多，也不会漂移。

#### 事件要特别处理：结果本身是随机的

「智慧圣殿」是 50% 攻击 +1 / 50% 生命上限 +3，「幸运骰子」是 ±金币 —— **选之前没法预告**。
所以：

| 层 | 事件 |
|---|---|
| 选前预告 | **不做**（结果随机，预告不了） |
| 选后确认 | **做**（快照对比自动生成） |
| HUD 微动 | **做** |

这就是快照对比的另一个好处：**它不关心变化是怎么来的**。

#### 验收

| 项 | 标准 |
|---|---|
| 奖励 | 选完「攻击 +1」，横幅显示 `攻击 5 → 6`，HUD 的「攻」滚动到 6 |
| 事件（确定型） | 选完「诅咒之井」，横幅显示 `生命 18 → 8` + `金币 34 → 74` |
| 事件（随机型） | 选完「智慧圣殿」，横幅显示实际抽到的那一项 |
| 无变化 | 选完什么都没改的选项，**不弹横幅** |
| 多变化 | 一次改 5 项以上时合并成"等 N 项"，不糊屏 |
| 不挡战斗 | 横幅出现时，战斗区（屏幕下方 3/4）不被遮挡 |
| 手机 | H=360 下横幅不压 HUD、不压角色 |

### 1.10 为什么数值成长本身不显眼

> 上一节讲的是"没看见"。这一节讲的是"看见了也可能没感觉" —— 两个不同的原因，都要修。

#### ① 取整台阶

伤害公式（`战斗2D.js:11193`）：

```js
var base = this.hero.attack * env * fury * rnd(0.85, 1.15) * (mult || 1) * ... + pass.flat;
```

普通挥砍 `mult = 1`，所以**平均伤害 ≈ 攻击力**，最终 `Math.round` 取整；敌人血量也是整数。
两件事叠加，攻击 +1 经常**换不来少一刀**。

实测（真实公式，种类系数取 `战斗2D.js` 的 `baseHp` ÷ `TIER_REF` `经典2D.js:595`）：

| 第 1 层 | 5 攻 | 6 攻 | 7 攻 | 8 攻 |
|---|---|---|---|---|
| 爪牙（8 HP） | 2 刀 | 2 刀 | 2 刀 | **1 刀** |
| 铁壁兵（13 HP） | 3 刀 | 3 刀 | **2 刀** | 2 刀 |
| 层主（18 HP） | 4 刀 | **3 刀** | 3 刀 | 3 刀 |

**前两次「攻击 +1」在第 1 层的杂兵身上是 0 变化。**

#### ② 两条曲线的斜率

| 曲线 | 公式 | 位置 | 每层增量 |
|---|---|---|---|
| 敌人血量 | `(floor × 2.5 + 5) × 种类系数` | `经典2D.js:632` | **+2.5 × 系数** |
| 玩家攻击 | 每层 4~6 间房、战斗房约 2~3 间，`攻击+1` 在 13 张奖励里出现率 23%（`主程序.js:6483`） | — | **期望 +0.5 ~ 0.7** |

**你在变强，但敌人变强得更快。** 用刀数表示（爪牙）：

| 层数 | 爪牙 HP | 修好后 | 不修（攻击卡在 5） |
|---|---|---|---|
| 1 | 8 | 2 刀 | 2 刀 |
| 5 | 18 | 3 刀 | 4 刀 |
| 10 | 30 | 3 刀 | **6 刀** |
| 20 | 55 | 4 刀 | **11 刀** |

**光 A 类那几个 bug，就能让后期的刀数翻倍。** 这就是"越打越打不动"的来源。

### 1.11 修法总览

> **具体任务、落点、验收、依赖全部在 §3 施工清单的批 1~4** —— 这里只留四条原则。
> 两处各写一份清单，迟早会漂移（项目里已经有过"图鉴手抄一份结果抄错"的教训）。

| # | 原则 | 为什么 |
|---|---|---|
| 1 | **先补通道，再补概念** | 通道不通时，任何"数值调整"都看不到效果，等于瞎调 |
| 2 | **一次覆盖全部入口** | 用 `withFeedback` 包六个入口，而不是给 20 个事件各写一句反馈 |

### 1.12 验收

| 项        | 标准                                       |

## 2. 议题二：垂直房间

### 2.1 2.9 为什么把它留到 3.0

《2.9版本初步设想》§2.4 的原话：`groundY`、`levelWidth`、平台带高度、HUD 遮挡**全部是按「横向 + 单层地面」推出来的**，  
改纵向要同时重算这四样；而且手机横屏 `H` 只有 360，纵向空间极其局促。

2.9 最后的选择是「不动相机模型」，把竖井 / 坠落井 / 蹬墙跳 / 钩爪整包留给 3.0。

**3.0 的做法：把房间转 90°**（§2.4）。这不是加一种骨架，是把整个关卡坐标系换掉 ——  
所以它确实是大版本级的改动，而不是 2.9.5。代价是 500~600 行（§2.9），作者说时间够，那就按真的做。

### 2.2 要打破的五个横向假设（实测）

| # | 假设                         | 代码                                                       | 现在的值                    |
| - | -------------------------- | -------------------------------------------------------- | ----------------------- |
| 1 | 只有一层地面                     | `this.groundY = H - 96`                                  | `战斗2D.js:8640`          |
| 2 | 房间是横向长条                    | `levelWidth = max(W*2, min(1400+floor*90, 2200))`        | `:8653-8657`            |
| 3 | 世界纵向只有 ±600                | `world.setBounds(0, -600, levelWidth, H + 1200)`         | `:8582`                 |
| 4 | 相机纵向余量 = 安全线 + 0.8 屏       | `cameras.main.setBounds(0, -head, levelWidth, H + head)` | `:8583`                 |
| 5 | 掉到 `groundY + 220` 以下 = 掉坑 | `if (h.y > this.groundY + PIT.triggerY) handlePitFall()` | `:13552`，`PIT` 在 `:646` |

另外一处要特别注意：

- **地面碰撞体是一行**。`layoutFloor()` `:8868` 把 `groundTiles` 按 x 索引铺成一条，一个 x 只有一个格子。  
  这决定了：横向房间的地面只能高低不同，不能上下重叠。  
  **竖塔的每层平台必须走 `spawnPlatformAt`（`:9519`，另一套碰撞池），不能走地面池。**
- **敌人只沿 x 铺**。`spawnEnemies` `:10015` 按 x 均分，然后从最高面往下掉（`:10003`）。  
  在横向房间这是对的；**竖塔里会全部落到井底**，必须改成沿 y 分布（§2.9 第 6 项）。

### 2.3 关键数字：手机横屏只有 200px

| 项                        | 值                              | 来源                                      |
| ------------------------ | ------------------------------ | --------------------------------------- |
| 手机横屏视口高                  | 360                            | 项目一贯的基准                                 |
| 顶部 HUD 下沿 `hudSafeTop()` | ≈ 157                          | `:8552`（注释原文："屏幕高度的 44%"）               |
| **可用战斗区高度**              | **≈ 200px**                    | 360 − 157                               |
| 满蓄力跳高                    | 1150² / (2 × 1700) ≈ **389px** | `CHARGE.maxPower` `:70`、`GRAVITY` `:50` |
| 桌面视口高                    | 720，可用区 ≈ 540                  | —                                       |

**两个结论：**

1. **层距必须 ≤ 240px**（200 可用高度 + 相机把玩家放偏下能多给 40px），  
   否则玩家永远在"盲跳下一层"。而满蓄力跳高是 389px ——  
   "技术上跳得上去"和"看得见跳得上去"是两件事，**按 389 设计会在手机上崩**。
2. 389px 的跳跃能力 > 220px 的层距，但 < 440px（两层的距离），所以**一次只能往上爬一层** —— 这是竖塔"能回头补漏"的前提（§2.10 ①）。  
   上和下用的是同一套机制：往下靠重力穿楼板，往上靠跳跃穿楼板。

### 2.4 真垂直 = 把房间转 90°

作者的原话：

> 进房间后宽度不变，房间向下延伸，视角也是向下移动，就像现在的横屏，  
> 房间高度是不变的，但长度变，垂直房间就这样倒一下，然后从左往右走变成从上往下走。

**这不是"多堆几个浮台"，是把整个关卡坐标系旋转 90°。**

|      | 横向房间（现状）                 | 垂直房间（竖塔）                    |
| ---- | ------------------------ | --------------------------- |
| 房间宽  | `levelWidth` = 1400~2200 | **`W`（一屏，横向不滚动）**           |
| 房间高  | `H`（一屏）                  | **`roomDepth` = 1400~2200** |
| "地面" | `groundY` 一条横线           | `floorY = groundY`（房间底）     |
| 边界   | 关卡两端是隐形墙                 | **左右两面真墙**                  |
| 前进方向 | 左 → 右                    | **上 → 下**                   |
| 相机   | 横向滚动                     | **纵向滚动，横向锁定**               |
| 地形   | 连续地面 + 浮台                | **每 220px 一层完整楼板，按 ↓ 下一层**  |

**为什么"往下走"在物理上是顺的**：重力方向不变（仍向下）。  
玩家进房在顶部，**按一次 ↓ 下一层** —— 完全顺重力，**不需要新移动技能，也不需要改重力**。  
（怎么做到的见 §2.5，机制引擎里已经有。）

**为什么"往上爬"也成立**：单向平台不挡从下往上（2.9.1 的改动），  
满蓄力跳高 389px > 层距 220px，所以能一层层爬回去。  
**上和下用的是同一套机制**（穿单向平台），只是一个靠重力、一个靠跳跃。

> **上一版的"竖井"是假的**：我设计的是"一屏高 + 3 个错位平台"，本质上只是双层的加厚版。  
> 真竖塔是"一屏宽 + 10 层平台 + 左右墙"，整个房间的坐标轴换了 —— 这是两件事。

---

### 2.5 怎么从上往下走：S 防御、↓ 穿一层

这是整个竖塔最核心的一件事，作者两句话把它定死了：

> **「防御为什么要占两个键，S 防御 ↓ 穿层不就好了，这样也不用特地跳一下了」**  
> **「而且不能一次下到底，只能一次下一层，不然直接就通关了房间还有什么意思」**

两条都对。上一版我犯的错是：

| 我上一版            | 问题                                         |
| --------------- | ------------------------------------------ |
| 说"必须改地面按下才能穿"   | 错。空中按 ↓ 本来就能穿，跳一下就行                        |
| 说"格挡走 K 键"      | **硬错**。`K` 是闪避，格挡是 `S` / `↓`（`:4101-4102`） |
| 设计成"按住 ↓ 一路穿到底" | **设计错**。10 层楼板等于白做，玩家直接掉到底开门走人             |

---

#### 键位拆分：防御归 S，穿层归 ↓

现在 `S` 和 `↓` 绑的是同一个功能（`guard` / `guard2`，`:4101-4102`），两处都在读：

| 读的地方                    | 现在                                               | 改成                                       |
| ----------------------- | ------------------------------------------------ | ---------------------------------------- |
| `updateGuard`（`:11521`） | `guard.isDown \|\| guard2.isDown \|\| guardHeld` | **只留 `guard` / `guardHeld`**（S + 触摸防御按钮） |
| `downHeld`（`:13592`）    | 同一个表达式                                           | **拆成 `guardHeld` 和 `dropHeld` 两个**       |

```js
// 现状 :13592
var downHeld = k.guard.isDown || k.guard2.isDown || ti.guardHeld || ti.downHeld;

// 改后
var guardHeld = k.guard.isDown || ti.guardHeld;   // S / 触摸防御按钮 → 举盾
var dropHeld  = k.guard2.isDown || ti.downHeld;   // ↓ / 摇杆下推   → 穿层
```

| 键        | 横向房间                      | 竖塔      |
| -------- | ------------------------- | ------- |
| `S`      | 防御                        | 防御      |
| `↓`      | **穿过脚下的单向平台**（新能力，原来要跳+↓） | **下一层** |
| 触摸「防御」按钮 | 防御                        | 防御      |
| 摇杆下推     | 穿过浮台                      | 下一层     |

> `↓` 在横向房间也能穿浮台，这是顺带的好处：原来"从浮台上下去"要跳一下再按 ↓，  
> 现在直接按 ↓ 就行。**和竖塔是同一套逻辑，不用写两份。**

---

#### 穿层规则：一次一层，必须落地再按

**只认"按下的那一瞬间"（JustDown），不认"按住"。**

```js
// 竖塔（以及任意房间的浮台）：站在可穿平台上，按下 ↓ 的瞬间
if (Phaser.Input.Keyboard.JustDown(k.guard2) || touchDropJustDown) {
  if (onGround && 站在可穿平台上) {
    this.setPlatformPassThrough(true);
    h.setVelocityY(120);          // 把脚从楼板上挪开
    this._dropUntil = now + 220;  // 220ms 后强制恢复碰撞
  }
}
// 每帧
if (this._dropUntil && now > this._dropUntil) {
  this.setPlatformPassThrough(false);
  this._dropUntil = 0;
}
```

**为什么是 220ms**：楼板视觉厚 28px，按 120 初速 + 重力 1700 算，220ms 内下落约 67px ——  
刚好穿过楼板，但远不到下一层（220px 下方）。所以**穿一层就停**。

**竖塔里还要禁掉"空中按 ↓ 连穿"**：`fastFall` 保留加速下坠，但**不开 `_platformPass`**。  
否则玩家跳一下按住 ↓ 就能一路穿到底 —— 又回到上一版的错。

```js
// :13594  竖塔里不开穿层，只加速下坠
var fastFall = !onGround && dropHeld && ...;
if (fastFall) {
  h.setVelocityY(...);
  if (this.roomSkeleton !== 'tower') this.setPlatformPassThrough(true);   // ← 加这个判断
}
```

#### 为什么"一次一层"不是限制，是玩法

作者那句"不能一次下到底，不然直接就通关了房间还有什么意思"点到了本质：

|           | 一路穿到底           | 一次一层                         |
| --------- | --------------- | ---------------------------- |
| 玩家做什么     | 按住 ↓，看 10 层楼板划过 | **每层落地 → 看有什么 → 决定打不打 → 再下** |
| 每层的怪      | 全部跳过            | **必须面对**（它就在你落地的地方）          |
| 10 层楼板的作用 | 装饰              | **10 次"要不要停"的决定**            |
| 房间时长      | 5 秒             | 40~60 秒                      |

**"一次一层"逼出了竖塔的全部玩法**：

- 落到第 3 层 → 有只远程怪在打你 → 打掉它还是马上再按 ↓ 躲到第 4 层
- 落到第 6 层 → 魂晶在这儿 → 拿（要停下来读条）还是先下去
- 落到第 8 层 → 血不多了 → 继续还是往回爬（能爬，但要一层层跳）

**如果允许一路穿到底，上面这些决定全部消失。** 所以这条不是手感参数，是设计红线。

---

#### 参数

| 参数              | 值                                       | 依据                                            |
| --------------- | --------------------------------------- | --------------------------------------------- |
| 房间宽             | **`W`（一屏）**                             | 横向完全不滚动 —— 这是"转 90°"的定义                       |
| 房间深 `roomDepth` | `min(1400 + floor × 90, 2200)`          | **直接复用现在 `levelWidth` 的公式**（`:8653`），只是搬到 y 轴 |
| 层距 `step`       | **220px**                               | 见下面验算                                         |
| 层数              | `round(roomDepth / step)` ≈ **6~10**    | 第 1 层 7 层、第 15 层 10 层                         |
| 楼板              | **整条**（0 ~ `W`），不设缺口                    | 下行唯一方式是按 ↓                                    |
| 楼板可穿            | **必须可穿**（不要设 `_solidDeck`，`:9561` 会跳过它） | 双层骨架的实体上层是不可穿的，竖塔不能照抄                         |
| 墙体              | 左右两面，从 `ceilingY` 到 `floorY`            | 实心碰撞，玩家出不去                                    |
| 出口              | 底部右端（`W - 100`, `floorY - 45`）          | 复用 `spawnPortal` 的写法                          |
| 进房点             | 顶部左侧（`140`, `ceilingY + 120`）           | —                                             |

#### 怎么让玩家知道自己在第几层（不用 HUD）

> **作者已定：不加 HUD 层数**（D3），靠视觉判断。
> 但这里有个坑：**如果每层楼板长得一模一样，视觉判断是不可能的** —— 玩家会彻底失去方位感。
> 所以必须给"楼层"一个**环境上的标记**。三个方案，成本从低到高：

| # | 做法 | 成本 | 效果 |
|---|---|---|---|
| 1 | **楼板左端刻"层号"**：1~10 道短线，像电梯楼层显示 | 极低（Graphics 画几根线） | 一眼看清，最直接 |
| 2 | **墙面随深度变暗**：越往下越暗，井底最黑 | 低（一条竖直渐变） | 有"往下走"的氛围，但读数不精确 |
| 3 | 每 3 层换一次墙面纹理（色带） | 中 | 能分"段"，分不出具体层 |

**建议 1 + 2 一起做**：刻痕给精确读数，渐变给氛围。两者都只用 Graphics，不加任何 UI。

> 刻痕的画法：`W - 24` 处（右侧墙边）竖排小横线，第 N 层画 N 道，
> 颜色用 `UI.muted`，不抢戏。玩家扫一眼就知道"我在第 6 层"。
> 这比 HUD 数字好在**不需要看别处** —— 它就在你脚下的楼板上。

#### 层距为什么是 220

| 量 | 值 | 算式 |
|---|---|---|
| 层距（相邻楼板顶面间距） | **220px** | 定值 |
| 楼板视觉厚度 | 28px | `spawnPlatformAt` 的薄板条 |
| **层间净空**（本层顶面 → 上层底面） | **192px** | 220 − 28 |
| 玩家身高 | 64px | 精灵帧高 |
| 守卫身高 | 60px | 精英守卫 `h: 50` × 1.2 缩放 |
| 玩家 + 敌人并排所需 | 124px | 64 + 60，**< 192 ✓** |
| **玩家头顶余量** | **128px** | 192 − 64 |
| 满蓄力跳高 | 389px | **> 220 ✓**（能爬一层，但 < 440 爬不了两层） |
| 层数 | 10 | 2200 / 220 整除 |

```
        ┌────────────────────────┐  ← 第 N 层楼板顶面
        │  头顶余量 128px         │
        │  ─ ─ ─ ─ ─ ─ ─ ─ ─ ─   │  ← 玩家头顶
        │  层间净空 192px         │
        │  ██ 玩家 64 + 敌 60 ██  │
        └────────────────────────┘  ← 第 N+1 层楼板顶面（220px 下方）
```

> **上一版这里算错了**：我写"净空 ≈ 128px"，那是"玩家头顶到上层底面的余量"，
> 不是净空。真正的净空是 192px —— 够放玩家 + 一只守卫，还有 68px 富余。
>
> 所以 220 不是"挤"，是"刚好"：**能并排站，但没有跳起来打的空间**。

> **手感**：贴地平推。跳劈靠"穿层下落"而不是"跳起来"（§2.10 ②）。
> 这是竖塔和横向房间最大的差别 —— 横向房间里跳劈是主力，竖塔里它是"下落时顺手用"。

### 2.6 敌人也会穿层追下来

这是"一次一层"的配套：如果玩家能下、怪不能下，那竖塔就是"玩家在楼上清、怪在楼下等"的割裂状态。

#### 三类敌人，三种穿层方式

| 类型 | 怎么跨层 | 为什么 |
|---|---|---|
| **近战怪**（chaser） | **穿楼板**（和玩家同一套 pass） | 它得追人，不能穿就永远留在上层 |
| **飞行怪**（fly） | **直接无视楼板**（本来就不撞地形） | 作者原话：「不然叫啥飞行怪」。现在 `spawnEnemy` 里飞行怪已经 `checkCollision.none = true`（`:10462`），竖塔里只要**保留这个行为**就对了 |
| **远程怪**（shooter） | **投掷物能穿层，但有上限** | 它站在上层往下射，弹道要能过楼板；但**不能无限穿**，否则站在顶层能打到井底 |

#### 近战怪：`dropChase` 状态

敌人状态机（`e.state`：`patrol` / `chase` / `windup` / `attack` / `charge` / `pounce`）加一个 `dropChase`：

| 项 | 值 |
|---|---|
| 触发 | 玩家在下方 > 120px，且自己站在楼板上 |
| 一次穿几层 | **一层**（和玩家同规则，200ms 后恢复碰撞） |
| 冷却 | **1.2s**（否则一群怪同时往下灌） |
| 不触发 | 正在起手 / 硬直 / 被击退中 |

```js
// updateEnemies 里，chase 之前判断
if (this.roomSkeleton === 'tower' && e.def.behavior === 'chaser'
    && now > (e.dropReadyAt || 0) && onLedge(e)
    && this.hero.y > e.sprite.y + 120) {
  e.state = 'dropChase';
  e.dropUntil = now + 200;
  e.dropReadyAt = now + 1200;
  this.setPlatformPassThroughFor(e, true);   // 单怪级别的 pass
}
```

> ⚠️ `setPlatformPassThrough` 现在是**全局**的（`:9557` 遍历所有 `platformTiles`），
> 敌人要用得改成"按精灵分组"或给敌人单独一条"忽略楼板"标记。**这是这一节唯一的实现难点。**

#### 飞行怪：什么都不用做

现在 `spawnEnemy` 里飞行怪已经 `spr.body.checkCollision.none = true`（`:10462`），
而且 `setAllowGravity(!def.fly)` 让它们不受重力。所以：

| 项 | 飞行怪 |
|---|---|
| 楼板 | **完全无视**（已经如此） |
| 世界边界 | **仍然受约束**（`setCollideWorldBounds(true)`，`:10467`） |
| 竖塔里要改的 | **一行都不用改** |

> 作者的提醒很关键：**"无视楼板"不等于"无视边界"**。
> 飞行怪可以穿过楼板自由上下，但撞到房间左右墙、天花板、井底还是要被挡住，
> 否则它们会飞出房间，然后被 `x > levelWidth + 120` 的兜底判成"脱离战斗"直接抹掉（`:16343`）。

#### 远程怪：投掷物能穿层，但有上限

远程怪站在上层往下射，箭/火球要能穿过楼板。但不能无限穿 —— 否则一只远程怪站在顶层，
整座塔都在它的射程里，玩家在井底也躲不开。

| 项 | 值 | 理由 |
|---|---|---|
| 能穿几层 | **1 层**（`pierceFloors: 1`） | 和玩家/近战怪的"一次一层"对齐 |
| 怎么实现 | 弹丸命中楼板时不销毁，`pierceFloors--`；减到 0 才停 | 复用弹丸的 `pierce` 机制（`:144` 远程配置里已有） |
| 命中楼板的表现 | 穿过时楼板闪一下 + 碎屑 | 让玩家知道"这一发是从上面来的" |
| 不穿的东西 | **墙**（左右边界）、**井底地面** | 边界是边界 |

```js
// 弹丸碰楼板时（新增判定）
if (isFloorTile(hit) && proj.pierceFloors > 0) {
  proj.pierceFloors--;
  sparkAt(proj.x, proj.y);      // 碎屑
  return;                        // 不销毁，继续飞
}
```

> 这条同时给了玩家一个**读招线索**：看到"楼板闪一下"，就知道上方有远程怪在射你。
> 正好呼应 §2.7 的"可学习"原则。

#### 为什么它解决了两件事

| 问题 | 怎么被解决 |
|---|---|
| **漏怪** | 玩家跳过的层，怪会自己追下来 —— 最后在井底汇合，门锁自然满足 |
| **塔是死的** | 玩家往下跑时，上面的怪在追 → 有"被追"的压力，不是空房间 |

#### 一个副作用要提前想好

如果 10 层的怪全部追下来，井底会变成"10 只怪的围殴"。所以：

- 冷却 1.2s 让它们错开落地
- **每层最多 1 只**（§2.5 参数），总量 6~10 只，和横向房间的 4~9 只同档
- 井底（最后一层）不放怪，留给"汇合" —— 否则玩家一下到底就被围死

### 2.7 机关陷阱：为什么不能照搬落石

#### 先看落石现在是什么

`spawnRockfall(x, surfaceY)`（`:9467`）：

| 项             | 值                                  |
| ------------- | ---------------------------------- |
| 预警时长 `warnMs` | **600ms**                          |
| 预警表现          | 地面阴影从 0.7 缩放到 2.2、alpha 0.16 → 0.5 |
| 文字提示          | 飘字「落石!」                            |
| 音效            | `sfx('spearwind')`                 |

作者的判断是准确的：**"前摇太长，大部分时间只能做装饰"**。  
600ms 是什么概念 —— 玩家跑速 250px/s（`:13623`），600ms 能跑 150px。  
所以落石**永远打不到人**，它的实际作用是"把玩家从这一块赶走"，是**区域封锁**，不是伤害。

#### 玩家的预测模型（要打破的就是这四条）

| # | 玩家默认相信       | 陷阱要做的                      |
| - | ------------ | -------------------------- |
| 1 | "有预警 → 我躲得开" | **预警可以只给一半**（只有声音，或者只在视野外） |
| 2 | "陷阱在固定位置"    | 位置每局重掷，不能背板                |
| 3 | "陷阱在地面上"     | 来自**脚下**、**头顶**、**侧面**     |
| 4 | "陷阱 = 伤害"    | 也可以是**位移**（把你打到下一层）        |

#### "出其不意"的三层模型（这是设计的核心）

| 层            | 玩家体验         | 怎么做到                 | 反面             |
| ------------ | ------------ | -------------------- | -------------- |
| **第一层 · 惊喜** | "卧槽，这也能有？"   | 第一次遇到时，**预警存在但在视野外** | 无预警直接扣血 = 不公平  |
| **第二层 · 知识** | "原来这个声音是它"   | 中招一次后，玩家能辨认征兆        | 征兆太隐蔽 = 等于没有   |
| **第三层 · 技术** | "我听到声音就提前走了" | 征兆 + 短预警，够反应但不能犹豫    | 预警太长 = 回到落石的老路 |

> **红线：不做"纯随机伤害"。** 玩家被阴了应该觉得"我漏看了线索"，不是"这游戏乱来"。  
> 所以每个陷阱都必须有**可学习的征兆**，只是第一次藏在视野盲区里。

#### 竖塔独有的三个"出其不意"资源

| 资源       | 为什么只有竖塔有                                                        |
| -------- | --------------------------------------------------------------- |
| **视野受限** | 一屏只看得到自己这层（§2.3 算过：上下都差 94~143px）→ 陷阱可以来自视野外                    |
| **纵向弹道** | 东西能从**下面**上来（横向房间只有水平弹道）                                        |
| **穿层动作** | 玩家按 ↓ 后的约 0.5 秒下落里，**不能格挡**（举盾要着地，`:11526`），**落点是盲的** → 天然的脆弱窗口 |

最后一条最关键：**穿层的瞬间是玩家最脆弱的时刻**，而玩家一局要穿 6~10 次。

> 注意：下落中**闪避仍然可用**（`tryDodge` 不检查 `onGround`），所以"穿层"不等于"必挨打"。  
> 脆弱的是"你不知道下面有什么"和"不能举盾"，不是"无法闪避" —— 这个区别决定了陷阱不能设计成必中。

### 2.8 五个陷阱

> 全部只在竖塔里做。横向房间一行不动。
>
> **先解决一个矛盾**：§2.5 说楼板是**整条**（0 ~ W，不设缺口），所以不能再用"某一块楼板"这种说法。
> 下面所有陷阱的"位置"都改成**整条楼板上的一个 x 区段** —— 碰撞不分块，判定只看 x 范围。

#### 通用参数

| 项 | 值 | 说明 |
|---|---|---|
| 触发判定 | 玩家 x 落在陷阱的 x 区间内 | 不分块，只看横向范围 |
| 陷阱宽度 | 穿刺 48 / 落板 96 / 夹击门 80 / 暗箭 48（墙面） | 都必须**小于预警时间内能跑出的距离**（250px/s × 预警时长） |
| 冷却 | 同一陷阱触发后 **3s** 内不再触发 | 防止连续吃同一招 |
| 无敌帧 | 闪避 / 受击无敌期间**不结算** | 不惩罚正确的操作 |
| 视觉层 | 画在楼板之上、角色之下（depth 2~3） | 不挡角色 |

#### ① 穿刺（脚下上来的）

| 项 | 值 |
|---|---|
| 位置 | 楼板下方，从玩家脚下刺上来；x 宽 **48px** |
| 触发 | 玩家站在该 x 区间内，且**停留 ≥ 0.6s**（不是一进来就刺） |
| 预警 | **0.25s**：楼板出现一个小孔（6px 黑点）+ 金属摩擦声 |
| 伤害 | 攻击力的 60%，击退小 |
| 怎么躲 | **横向走出 48px**（0.25s 内跑 62px，够）或跳起来 |
| 为什么出其不意 | 玩家注意力在**水平方向的怪**上，脚下是盲区；"东西从下面来"在横向房间不存在 |
| 怎么学 | 小孔 + 金属声。第二次听到就知道低头看 |

#### ② 坠物（头顶掉下来的）

| 项 | 值 |
|---|---|
| 位置 | 上层楼板 → 砸到玩家所在层；落点 x 宽 **64px** |
| 触发 | 玩家进入落点范围时**立刻**触发（不等停留） |
| 预警 | **0.35s，只有声音**（石块松动 + 下坠风声），**没有地面阴影** |
| 伤害 | 攻击力的 80%，击退中 |
| 怎么躲 | 横向走开 64px（0.35s 内跑 87px，够），或**举盾**（S） |
| 为什么出其不意 | 玩家**看不到上层**（视野差 143px），只能靠听。落石有阴影是因为它在你视野内，坠物没有 |
| 怎么学 | 声音有左右声道差异（从左/中/右来），听两次能分辨 |

> 这一条是对落石的直接改造：**同样是从上往下砸，把"视觉预警 600ms"换成"听觉预警 350ms"**。
> 玩家躲不掉第一次，但躲得掉第二次 —— 这就是"惊喜 → 知识"。

#### ③ 落板（站久了会塌）

| 项 | 值 |
|---|---|
| 位置 | **整条楼板上的一个 96px 区段**（视觉上画裂纹，碰撞不分块） |
| 触发 | 玩家站在该 x 区间内，**累计停留 ≥ 2.5s**（离开会缓慢回落） |
| 预警 | **0.5s**：裂纹扩散 + 轻微抖动（视觉，看得见） |
| 效果 | **不伤害**，玩家掉到下一层 |
| 怎么躲 | 离开这个 96px 区段 |
| 为什么出其不意 | 第一次不知道哪段会塌；而且它**逼玩家不要在一层停太久** —— 和"一次一层、慢慢清"的节奏正面对抗 |
| 怎么学 | 裂纹 + 抖动，很明确 |

> 这个陷阱的价值不在伤害，在于**它是唯一一个"惩罚犹豫"的陷阱**。
> 玩家在层 5 想"打不打这只怪"，犹豫 3 秒，楼板塌了，掉到层 6 —— 决定被外力做掉了。
>
> 注意：落板不伤害，但掉到下一层会**落在怪的旁边** —— 真正的惩罚是"你失去了准备时间"。

#### ④ 夹击门（上下合拢）

| 项 | 值 |
|---|---|
| 位置 | 玩家所在层与上一层之间的空隙，**横向 120px 的一段**（不是整层） |
| 触发 | 玩家站在该 x 区间内，且**停留 ≥ 0.4s** |
| 预警 | **0.4s**：上下楼板同时抖动 + 石头摩擦声 |
| 伤害 | 攻击力的 100% + 硬直 0.6s |
| 怎么躲 | **横向跑出 120px**（0.4s 内跑 100px，**不够**）→ 所以真正的躲法是**提前不站进去**，或者**跳起来**（合拢有 60px 的缝隙，玩家身高 64 挤不过去）→ **只能靠不站进去** |
| 为什么只有竖塔能做 | 需要"上下都有楼板"的结构，横向房间没有 |
| 怎么学 | 抖动很明显，但**0.4s 不够跑出去** —— 它是"惩罚贪刀"的陷阱 |

> **这一条要重新算**：0.4s 跑 100px < 120px 的宽度，玩家跑不出去。
> 所以它要么是"必吃"（不公平），要么必须满足下面任一条：
>
> | 修法 | 效果 |
> |---|---|
> | 宽度降到 80px | 0.4s 跑 100px > 80px，**能跑出去** |
> | 预警延长到 0.55s | 跑 137px > 120px，能跑出去 |
> | 触发条件加"停留 ≥ 0.4s" | 玩家看到抖动时已经在里面了，仍然跑不出 → **无效** |
>
> **采用：宽度 80px + 预警 0.45s**（跑 112px > 80px，留 32px 余量）。
> 这样它是"看到抖动就跑"的陷阱，而不是"必吃"。

#### ⑤ 暗箭（侧墙射的）

| 项 | 值 |
|---|---|
| 位置 | 左右墙 → 水平射向房间内，**从墙面射到对面墙** |
| 触发 | 玩家进入该层的**整条楼板**时随机触发（每层最多 1 次） |
| 预警 | **0.3s**：墙上出现小孔 + 上膛声 |
| 伤害 | 攻击力的 50%，击退中 |
| 怎么躲 | **跳**（箭贴楼板上方 24px 飞过，玩家跳起 80px 就躲开了） |
| 为什么出其不意 | **竖塔的墙是新东西**，玩家不知道墙上会有机关（横向房间的墙是隐形边界，什么都没长） |
| 怎么学 | 墙上的孔 + 上膛声 |

> 暗箭的"怎么躲"是**跳**，而穿刺的"怎么躲"是**走**，坠物是**听**，落板是**离开**，夹击门是**别站进去** ——
> 五个陷阱五种躲法，这是刻意的：**同一个动作不能躲所有陷阱**，玩家必须读招。

#### 数值总表

| 陷阱 | 预警 | 伤害 | 附带 | 抽中权重（陷阱层内） |
|---|---|---|---|---|
| 穿刺 | 0.25s | 60% | 击退小 | 25% |
| 坠物 | 0.35s（仅声音） | 80% | 击退中 | 25% |
| 落板 | 0.5s | 0 | 掉下一层 | 17% |
| 夹击门 | 0.45s | 100% | 硬直 0.6s | 13% |
| 暗箭 | 0.3s | 50% | 击退中 | 20% |

> **注意口径**：这张表是"**已经确定这一层有陷阱**时，五种里抽中哪个"的权重（合计 100%），
> 不是"每层独立掷五次"。否则五者相加 60% 只是巧合，实际会算出"一层里可能同时有 3 个陷阱"。
> 正确的掷法见下面：先掷"有没有"，再掷"是哪个"。

**作者已定：每层 60% 概率有陷阱。**

```
第 1 掷：有没有陷阱      40% 无 / 60% 有
第 2 掷（有陷阱时）：    80% 单个 / 20% 两个
第 3 掷：抽哪个           按上表权重，两个时不重复
井底层：强制跳过，0%
```

于是全局分布是：**40% 无 / 48% 单个 / 12% 双个**。

10 层就是 6 层有陷阱 —— 密度不低，所以另外两条约束必须守住：

| 约束 | 理由 |
|---|---|
| 双陷阱只能是"有解"的组合（见下面搭配表） | 无解组合等于送死 |
| 井底层不放陷阱 | 那是汇合决战的地方 |

> 密度高的好处是**玩家会开始记位置**（这是"知识层"）；坏处是"惊喜"会衰减。
> 所以批 8 的验收要专门测这一点：第 1 层遇到陷阱 vs 第 8 层遇到陷阱，紧张感是否一样。

#### 与怪的搭配（允许叠加，鼓励配合）

> **作者更正**：「同一层放多个陷阱也没事啊，可以让陷阱之间打配合」。
> 上一版我写"不许叠加"是过度保守 —— 叠加不是问题，**没有解的叠加才是问题**。

**判断标准只有一条**：玩家有没有至少一条**能走通的应对**。

| 组合 | 有没有解 | 判定 |
|---|---|---|
| 穿刺 + 坠物（脚下 + 头顶） | 有：**横向走开**（两个都是纵向的，水平移动同时躲开） | ✅ 好的配合 |
| 穿刺 + 暗箭（脚下 + 侧墙） | 有：**跳**（跳起来躲穿刺，暗箭从脚下高度过） | ✅ 好的配合 |
| 落板 + 穿刺 | 有：**别站那儿**（落板逼你走，穿刺逼你跳） | ✅ 好的配合 |
| 坠物 + 夹击门 | **没有**：上下同时封死 | ❌ 禁止 |
| 三个同时 | 通常没有 | ❌ 最多两个 |

#### 允许的搭配表

| 组合 | 应对方式 | 强度 |
|---|---|---|
| 穿刺 + 坠物 | 横向移动 | 中 |
| 穿刺 + 暗箭 | 跳 | 中 |
| 落板 + 穿刺 | 移动 + 跳 | 中 |
| 坠物 + 暗箭 | 斜向跑 | 中 |
| 落板 + 坠物 | 快速离开这一层（按 ↓ 走） | 强 |
| 夹击门 + 暗箭 | 跳到夹击门上沿（夹击门只在下半段合拢） | 强 |
| **夹击门 + 坠物** | **无解** | **禁止** |
| **夹击门 + 穿刺** | **无解**（上下夹 + 脚下刺） | **禁止** |

#### 与怪的关系

| 规则 | 原因 |
|---|---|
| 陷阱层**可以放近战怪**，但陷阱必须是"能躲开"的那一类 | 近战 + 能躲的陷阱 = 走位压力；近战 + 无解陷阱 = 送死 |
| **无解组合的层不放怪** | 上面已经够难了 |
| 井底层不放陷阱 | 那是"汇合决战"的地方 |
| 同一层最多 **2 个**陷阱 | 三个以上基本凑不出"能走通的应对" |

#### 一个额外的好处

陷阱之间配合，比"陷阱 + 怪"更有意思：

- 怪的威胁是**主动追你**，玩家能预判；
- 陷阱的威胁是**固定的**，玩家能记位置；
- 两个固定陷阱配合出来的"死亡夹角"，玩家要靠**读位置**去解 —— 这是纯空间智力，
  和"躲怪的招式"是两种不同的紧张感。

所以竖塔的难度曲线可以做成：**单陷阱 → 单陷阱+怪 → 双陷阱配合 → 双陷阱+怪**。

### 2.10 三个关键决策（已定）

#### ① 漏怪怎么办 → **已定：敌人追下来**

门锁是 `clear`（清完所有敌人才开门），竖塔有 6~10 层。
如果玩家冲到第 8 层发现第 2 层漏了一只，要爬 6 层回去。

**为什么这个问题比横向房间轻**：因为"一次一层"（§2.5），玩家**必然在每层落地**，怪就在落点旁边。
漏怪的概率比"一路穿到底"低得多。剩下的只是"落地→立刻再按 ↓ 跳过某层"。

**定案**：敌人会自己追下来（§2.6 的 `dropChase`）。

| 好处 | 说明 |
|---|---|
| 漏怪自己会补 | 跳过的层，怪追下来，最后在井底汇合，门锁自然满足 |
| 塔是活的 | 玩家往下跑时，上面的怪在追 → 有"被追"的压力 |
| 不新增移动逻辑 | 和玩家共用"穿单向平台"，只是敌人不用按键 |

**被否掉的两个方案**（留档，免得以后重新讨论）：

| 方案 | 为什么不用 |
|---|---|
| 门锁改成"到达底部" | 变成跑酷房，战斗变可选，和现有 `clear` 目标不一致 |
| 门锁改成"清掉 ≥80%" | 要改目标系统，而且"80%"很难让玩家理解 |

#### ② 层距定 220，但要保住跳劈（**作者已定**）

> 作者原话：「V6 就现定的 220 层距，保留跳劈」。
> 所以不是"220 还是 260"的二选一，而是**220 也要能用跳劈**。

220 层距下净空约 128px，正常"跳起来再砸"确实不够。但竖塔有一个横向房间没有的机会：
**按 ↓ 下穿的那 0.5 秒，人本来就在下落。**

| 场景 | 横向房间 | 竖塔 |
|---|---|---|
| 跳起来砸 | `DIVE.mult: 1.9`，主力 | 净空不够，用得少 |
| **穿层下落中砸** | 不存在 | **变成主力**：按 ↓ 下穿 → 落到下一层前按 J → 砸在下一层的怪头上 |

**代码上不用改判定**：`tryAttack` 里"非着地 → `tryDiveAttack`"（`:10564`）已经覆盖了这个场景 ——
穿层下落时人不是着地状态，按 J 自然就是跳劈。

**要调的是倍率**。现在 `DIVE.mult: 1.9` 是"从高处砸下来"的固定奖励；
竖塔里落差固定 220，建议改成**按已下落距离递增**：

```js
// 现在的固定倍率
mult: DIVE.mult                    // 1.9

// 竖塔：下落越远越狠（穿两层再砸 > 穿一层就砸）
var fallBonus = this.roomSkeleton === 'tower'
  ? Math.min(1, (this.hero.y - this._dropStartY) / 220) * 0.4
  : 0;
mult: DIVE.mult + fallBonus        // 1.9 ~ 2.3
```

> 这条让竖塔有了自己的核心连招：**↓ 下穿 → J 跳劈 → 落地打**。
> 横向房间的跳劈是"跳起来砸"，竖塔的跳劈是"掉下去砸" —— 同一个动作，两种来源。
> 也顺带解释了为什么"一次一层"不无聊：**每一层都是一次跳劈机会**。

#### ③ 出口位置 → **已定：底部右端**

| 方案 | 改动量 | 结论 |
|---|---|---|
| **底部右端**（`W - 100`, `floorY - 45`） | 复用 `spawnPortal`（`:10547`）的写法，**零改动** | ✅ 采用 |
| 底部正中央 | 要改传送门定位 + 相机取景 + 地图节点朝向 | ❌ 不值得 |

> 出口在右端还有个好处：**它和"进房点在左上"形成一条对角线**，
> 玩家从左上进、右下出，天然要走完整个房间的对角，不会漏掉一层。

- `populateTowerCrystals`：在楼板层里随机挑 1~2 层（跳过出生层与井底），一律落在楼板顶面上。
- 出口：`spawnPortal` 的 `levelWidth − 100 / groundY − 45` 在竖塔里自动就是"底部右端"，**零改动**（文档 S5 成立）。
- 掉落回传：`nearestTowerDeckY(y)` + `teleportHeroTo(x, {y})`；掉出井底回井底，而不是"缺口右侧"。

### 批 7 · 敌人穿层追击

- **7.1 单怪级别 pass**：改成给两条 collider 挂 `processCallback`（`heroTileFilter` / `enemyTileFilter`），
  **不再去关平台 body**。这一条比文档写的更关键：文档说"`setPlatformPassThrough` 改成单怪级别"，
  但那个函数改的是**共用碰撞体**，只要动它就一定会波及同一层的所有实体。
  最终方案是**玩家与敌人各走各的过滤器**，`setPlatformPassThrough` 只留给横厅的加速下坠（既有回归在验它）。
- 7.2 `dropChase`：`state='drop'` + 200/220ms 放行窗口 + 1.2s 冷却，只对 `chaser / charger`；
  穿层期间不出手（与"玩家穿层不能举盾"对称）。
- 7.3 飞行怪"无视楼板但仍受边界"零改动成立；远程弹丸 `pierceFloors = 1`，
  命中楼板时**不销毁**、楼板闪一下（`flashTowerDeck`）—— 顺带成了"这一发从上面来"的读招线索。

### 批 8 · 陷阱（先两个）

### 批 9 · 参数化进抽签 + 剩余三个陷阱

### 批 5~9 的视觉验收修正（截图后才发现的三个问题）

测试全绿不等于「看起来对」。把竖塔真跑起来截图之后改了三处：

| 问题 | 现象 | 修法 |
|---|---|---|
| **出生时头顶缩在 HUD 后面** | `TOWER.topPad = 200` 是定值，而手机横屏 `hudSafeTop ≈ 157` —— 只留 43px，玩家站上第一层楼板时头顶（64px 高）整段在 HUD 后面 | `towerTopPad = max(200, hudSafeTop + 96)`；桌面不变，手机上第一层整体下移（层数照旧，只是房间顶部留白变大） |
| **目标敌人面板盖住出生点** | 面板的"最近敌人"只按 **x 距离**挑，竖塔里"下面三层那只怪"会把面板点亮，而面板正好占据屏幕左侧出生区 | ① 最近敌人在**屏内**（x 与 y 都要在视口内）的里面挑；② 竖塔出生点从 `140` 右移到 `0.30W`（≈384），让开左侧那一列 HUD；③ 敌人投放下限从 `0.38W` 提到 `0.45W`，不会一进房就贴脸 |
| **敌人血条画进 HUD** | 竖塔里血条会跟着敌人卷到 HUD 后面，压在按钮行上 | `updateEnemyMeters` 里判 `by < hudSafeTop` 就不画（那一段反正读不到，画上去只是噪音） |

> 顺便把层号刻痕从 `1.6px / 55%` 加到 `2px / 66%` —— 1384×797 的截图里原来的刻痕几乎看不见，
> 而"一眼看出第几层"是它存在的唯一理由。

> 以下是**需要更正**的部分 —— 其中 ①②③④⑤ 是会影响施工的结论性问题。

### ① A4「护盾只有单向同步」漏了一半：引擎**加**盾也会被抹掉

文档只写了"引擎扣盾、内核不知，任何 pushStats 都把盾补回内核值"。
实测还有反向的一半：战士每房间开局 **+3 盾**（`applyRoomStartPassive`）、魂晶回盾、
完美格挡回盾、药水回血都是**引擎单方面加的**，内核同样不知道 ——
下一次 `pushStats` 会把它们**抹掉**。玩家体感是「战士的坚韧之盾刚出来，进商店就没了」。

**修法**：`consume` 必须配一个对偶的 `gain`，两者都不回推。只补 consume 的话，
批1 的验收（扣光盾拿遗物不满盾）能过，但会有另一个方向的新 bug。
→ 已在批 1 实现 `bridge.gain`。

### ② B3「`pendingAttackBoost` 2D 不读」定位不准：是**铁定不会执行的路径**

真实情况：2D 里 `prepareStrengthPotion()` **根本不会被调用** —— 它只在 `state.mode === 'bossPrep'`
（文字模式 Boss 前那个专属界面）里生效，而 2D 没有那个界面。所以不是"写了不生效"，是"那段代码在 2D 里永不执行"。
→ 修法从"废弃或改写"变成"在 2D 接管时直接返回"，字段继续服务文字模式。

### ③ §1.1 的"面向结果编程"还有一处没被查到：图鉴「增益」手抄了 13 条

内核里其实有**三份**增益表：`fullBonuses`（28 项）、一份 **13 项的手抄表**、`BONUS_POOL`（30 项，唯一的实现）。
而 DOM 图鉴「增益」读的是那份**手抄的 13 条** —— 既漏了 17 项，描述也停在文字模式
（"每回合获得 2 点护盾"，而批2 之后那是"每房间开始"）。
→ 批 3 顺手改成读 `BONUS_POOL`（与「遗物」「道具&商品」两条同一个原则）。

### ④ §2.9 第 4 项「相机横向锁定 + 纵向跟随」低估了：横厅那套跟随参数**不能复用**

横厅的 `applyCameraFollow` 是"死区 + followOffset"，参数是按"可用区 ≈ 540px（桌面）"推出来的；
手机 H=360 时 `bandTop ≈ 213`、`H−28 = 332`，死区只剩 119px，**已经贴到极限**。
竖塔的可用纵向空间里还多了"要看下一层"，这套参数放不下。
→ 竖塔改成**手动纵向滚动**（`cam.stopFollow()` + 每帧 lerp 到 `hero.y − anchor`），
横向靠"世界宽 = 视口宽"自然锁死。文档说"横向锁定"，实际不需要任何额外代码。

### ⑤ 文档没预见「抽签 × 显式机制」的冲突（实测踩到）

调试 / 预览页会显式指定 `mechanic: 'collapse'`，而批 9 之后抽签表里有 8% 是竖塔；
竖塔**不挂机制**（塌陷按 x 分段、守点圈在地面）——于是那 8% 的塌陷房变成"有机制标记、没有机制"，
**解不开门**。P0-P3 回归立刻红了两项（塌陷解封 / 过门计数）。

→ 修法：`isVerticalRoom` 与 `pickSkeleton` 的预抽签**都**排除"带 mechanic 的房"。
两处判断必须一字不差，否则就是"抽到了竖塔、坐标系却没转"的半成品房间。

### ⑥ §3 的「365 项断言一项都不该变色」不成立 —— 而且这次是**对的**

加第四种骨架后，三条老断言（P0-P3 的"平厅 ≈40% / 双层 ≈35% / 断桥 ≈25%"、2.9.2 的"第 6 层起回到 50/30/20"）
**必然变化**：40/35/25 → 35/30/20/15。这不是"动错了地方"，是设计变更本身。

→ 处理方式：按**新设计**更新区间，并**补一条竖塔断言**。回归从 365 项变成 **367 项**，
覆盖反而比原来更全。原文那句"变了说明动错了地方"应当加一条例外：
**"当变更本身改变了分布，断言要跟着改，并且要补上新维度的那一条。"**
